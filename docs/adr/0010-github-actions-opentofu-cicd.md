# CI/CD runs on GitHub Actions with push deploys; infrastructure is OpenTofu + Helm + a scripted Vast.ai layer

CI/CD is GitHub Actions (now an explicit decision, not an inherited assumption): the public repo gets unlimited free minutes on standard runners, and the code, secrets store, and registry already live under the same account. The flow is trunk-based full continuous deployment to a **single production environment** — merge to master → path-filtered build + tests per monorepo area (ADR 0006) → auto-deploy — with no staging until its absence hurts (recorded trigger for revisiting). Deploys run `helm upgrade` through an **SSH tunnel** over the already-open port 22 to the K3s API, authenticated by a **namespace-scoped ServiceAccount-token kubeconfig** — never the admin `k3s.yaml`, whose embedded certs K3s rewrites on restart and silently invalidates within a year. Database migrations ship as an EF Core migration bundle executed by a Helm pre-upgrade Job, so a failed migration halts the rollout by construction.

Infrastructure-as-code is a three-zone split, all reading truth from files in the repo:

- **OpenTofu owns the platform layer**: Hetzner server + firewall (K3s installed via cloud-init, so a dead box rebuilds with one apply), Cloudflare DNS + R2 buckets (lifecycle/CORS), and the B2 bucket. State lives client-side-encrypted in a private R2 bucket with S3-native lockfile locking. OpenTofu over Terraform because it fixed the AWS-SDK checksum breakage against third-party S3 stores in core (Terraform's remains an open issue with an env-var workaround) and adds native state encryption; same HCL, identical provider versions, skills transfer 1:1.
- **Helm owns everything inside the cluster** (ADR 0009), running from CI on every merge. Deliberately not driven from OpenTofu: the layers have opposite tempos.
- **A versioned config + idempotent Python script over Vast's official SDK owns the Vast.ai serverless definitions** (template, endpoint, workergroup) — no credible Terraform/OpenTofu/Pulumi provider exists, and scripted CLI/SDK automation with minimal-permission API keys is Vast's own documented CI story (`docs/research/vastai-provisioning-automation.md`). Per worker-image release the script updates the template tag, repoints the workergroup at the returned new content hash, and triggers Vast's documented zero-downtime rolling worker update. Vast's beta "Deployments" workflow is the recorded runner-up once it matures. GitHub repo settings stay deliberately unmanaged.

Secrets are **GitHub Environment secrets only**, injected at `helm upgrade` into Kubernetes Secrets. Every secret in the design (R2/B2/Vast keys, SSH deploy key, SA token, DB password) is re-issuable at its source, so no copy-of-record store exists; a names-only runbook file in the repo records where each is re-issued. GitHub secrets are write-only — a cache, not a source of truth. SOPS+age (the self-hoster standard) was rejected because the public repo would publish ciphertext forever; it returns if the repo goes private or Flux is adopted.

Images live on **GHCR**: free for public images, no published pull-rate limits, one hard rule of 10 GB per layer (constraint handed to the worker-image ticket, with byte-stable model layers so unchanged fat layers are never re-transferred). Docker Hub was eliminated — its 100 anonymous pulls/IP/6 h quota is shared by every tenant behind a Vast host's IP. A self-hosted registry on R2 (distribution v3, ~$0.45/mo, free egress) is the recorded fallback and the GHCR-outage answer alongside warm workers and Vast host layer caching. Builds: routine images (backend, thin worker layer) on free standard runners with disk maximization (~50–60 GB scratch); the rare fat model-base build (if the worker-image ticket bakes models) on an **ephemeral Hetzner VM created and destroyed per build** (cents per run — no standing machine, so the public-repo self-hosted-runner fork-PR risk never arises); laptop build documented as manual fallback.

Consequences: a solo operator auto-ships to production guarded only by CI tests and the migration-halt Job (accepted; deploy blips are moot per the pipeline design and rolling updates); GitHub outages block shipping but never production — a break-glass runbook entry covers "fix while GitHub is down" (build locally, `docker save` over SSH into K3s, `helm upgrade` over SSH — a place the push model beats pull); Python enters the repo for one deploy script (Vast's SDK; consolidation into a C# tool sharing the dispatcher's REST client stays open, it's all documented REST underneath); Flux-pull is the designated growth path (dissolves deploy access, adds drift reversion — at ~1 GB RAM, new concepts, and forced SOPS), Tailscale the later operator-access upgrade (close every public port), Cloudflare Tunnel the noted zero-open-ports alternative.

## Considered Options

- CI: GitHub Actions (chosen) — free, native, zero setup; self-hosted CI (Woodpecker/Jenkins — a service to operate before the product exists), other hosted CI (second vendor, no upside), GitLab move (re-platforming for nothing).
- IaC tool: OpenTofu (chosen); Terraform — same tool, open R2 checksum bug + no state encryption, otherwise legitimate with workaround; Pulumi C# — language unity, but weak blob-storage locking (no conditional writes), unverified R2 pairing, B2 provider via ad-hoc bridge. Survey: `docs/research/cicd-iac-landscape.md`.
- Deploy access: SSH tunnel + scoped SA token (chosen); exposed 6443 (standing scanner target), Tailscale (third-party SaaS in deploy+admin path), Cloudflare Tunnel (daemon + vendor in admin path), Flux pull (deferred per ADR 0009, forces SOPS).
- Secrets: GitHub Environment secrets + re-issue runbook (chosen); SOPS+age (publishes ciphertext in a public repo), sealed-secrets (key dies with the box), Vault/ESO/SaaS managers (team-scale machinery for six re-issuable secrets).
- Registry: GHCR (chosen); Docker Hub (shared-IP pull quota on Vast hosts), Quay/ECR Public/GAR (new vendor, no advantage), self-hosted on R2 (recorded fallback, not default — an endpoint to run and secure).
- Build machines: free runners + ephemeral Hetzner VM for fat builds (chosen); standing self-hosted runner (~€25/mo + public-repo fork-PR exposure — dominated by the ephemeral form), GitHub larger runners (paid and Team/Enterprise-org-only).
