# Clerk is the identity provider; users are mirrored into our Postgres

Accounts and sign-in are outsourced to [Clerk](https://clerk.com) rather than built into the backend. Decided while resolving [Auth and accounts approach (#11)](https://github.com/Astral100/SeedVr.Backend/issues/11), on the research in [`docs/research/auth-providers.md`](../research/auth-providers.md) (three verified passes: provider survey, bundled-extras check, Clerk availability track record).

- **What Clerk carries**: registration and sign-in (e-mail + password and Google), the prebuilt frontend components, bot protection on signup (Cloudflare Turnstile, all plans), verification and password-reset e-mails sent from our own domain with no mail provider of ours, and a user-management dashboard. Open signup from day one.
- **Plan path**: free Hobby plan first (fixed 7-day sessions), upgraded to Pro (~$25/mo) when 30-day sliding sessions, user bans, or Clerk-branding removal are wanted. No SLA below Enterprise.
- **Our side**: the API validates Clerk's short-lived RS256 session JWTs statelessly against Clerk's JWKS (plain `AddJwtBearer`). A `users` table in our Postgres mirrors Clerk via its documented pattern — webhook upsert on `user.created`/`updated`/`deleted`, keyed on the Clerk user id, idempotent against at-least-once delivery — plus create-from-token when a not-yet-mirrored user calls. Every job and input file carries its owning user; every query filters by the caller.
- **Two-sided soft delete**: Clerk's self-service delete stays disabled; "delete my account" is our endpoint, which marks the user deleted locally and bans them in Clerk (sessions revoked, record intact; pre-Pro: session revocation + our deleted-mark). Restore inside the grace period (default 30 days, tunable config) is unban + unmark. When the period lapses, the periodic deletion pass erases both sides: our rows and stored files, and Clerk's record via its delete-user API.
- **Seams left for later efforts**: a billing/credits attachment point on the user record and one always-approve affordability gate at job submission (billing is its own effort); no admin surface in v1 (Clerk's dashboard covers account chores; an admin screen waits for concrete needs); quota policy stays unspecified.
- **Accepted knowingly**: US-only data residency for user identities; Clerk downtime is our downtime — verified record: ~2.4 h of hard full outages in the trailing year (worst 90 min) plus one ~3.75-day intermittent-failure stretch (Sep 2025), with every signed-in user dropped within a minute of a full outage because the 60-second tokens stop re-issuing. Running GPU jobs are unaffected (workers never talk to Clerk).
- **Exit path (verified)**: full self-serve export including bcrypt password hashes; leaving Clerk means rebuilding sign-in UI on the recorded fallback — ASP.NET Core Identity in the API — not resetting anyone's password.

## Considered options

- **ASP.NET Core Identity inside the API** — the recorded fallback: $0/mo, users in our own backed-up EU Postgres, no added downtime source; loses on build effort, most of it the future frontend's sign-in/account screens plus assembling Turnstile and a mail provider ourselves.
- **Auth0** — free 25k MAU with an EU region, but bot detection is an Enterprise add-on and production e-mail requires our own mail provider; its remaining edge (EU residency) didn't outweigh Clerk's bundle.
- **Supabase Auth** — free CAPTCHA and 50k MAU, but users would live in a second managed Postgres beside ours, and production e-mail is bring-your-own anyway.
- **Self-hosted identity servers (Keycloak, Zitadel, Duende)** — none earn their keep at 10–100 users against Identity-in-API; Duende Community Edition noted as the no-re-platforming seam if third-party SSO ever appears.
