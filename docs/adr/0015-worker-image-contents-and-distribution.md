# Worker image contents and distribution

The worker image is baked, layered, and distributed from our own registry. Contents: a pinned Vast ComfyUI base at the latest stable ComfyUI (≥0.30, so the CRF/bit-depth parameters are honored — older versions ignore them silently; each new image is verified by running the POC console app against it), the SeedVR2 node pack at a pinned commit, the stock ai-dock wrapper (used as-is, never forked), and our worker agent as a self-contained single-file .NET program — nothing is installed into the image's conda-managed Python, whose fragility the storage probe demonstrated (a pip install reported success while the package stayed unimportable). Model files are baked into the image, one layer per file, byte-stable across releases, with a thin code layer on top: a code release re-ships megabytes, not models, and image variants (full vs single-model) are layer selections, not separate builds. Baking beats a startup download because a broken image never starts and gets rescheduled, while a broken download produces a worker that looks alive and must be caught by us.

Shipped model set (~57 GB): 3B fp16, 7B and 7B-sharp each in fp16 and the fp8 `mixed_block35` variant, shared fp16 VAE. The plain-fp8 3B is excluded (measured RoPE-quantization damage — numz issue #610). Precision reaches a job as an ordinary parameter: presets pick it on the simplified path, advanced mode exposes the exact file — so a later default flip is preset content, not an API or UI change. An fp16-vs-fp8 seam A/B on our own content is a required early implementation item. The int8-ConvRot set is deliberately deferred: it loads only in ComfyUI's brand-new native nodes (not our node lineage), its quality is unvalidated, and it carries open bugs — but adopting it once validated is a high-priority post-v1 backlog item.

Distribution: a self-hosted CNCF Distribution (registry:3) on the existing Hetzner box with Cloudflare R2 as the storage backend and presigned-redirect blob downloads, so workers fetch the gigabytes straight from R2. Downloads are free at any volume (~$1.35–4.35/mo for 100–300 GB stored, operations within free tiers); the 16.5 GB fp16 files face no layer cap; and pulls avoid GHCR's documented, year-plus-unresolved EU peak-hour degradation. A registry outage affects only new rentals and rollouts, never running workers or the warm floor. Rollout is provisioner turnover: bump the release tag in configuration and new rentals use it; busy workers finish and retire. No staging endpoint at v1 — a post-release smoke job (one small real job through production) is the safety net, and a staging setup is planned as a fast-follow after launch. The machine pool is open (no Secure Cloud pinning), revisitable as a single search-filter change.

## Considered Options

- Startup model download from R2 (POC-style). Rejected — reintroduces the running-but-broken failure mode and self-policed readiness; a fresh host pays the transfer either way.
- GHCR (ADR 0010's registry) for the worker image. Rejected for this image — hard 10 GB/layer cap versus 16.5 GB fp16 files, plus a documented unresolved EU peak-hour collapse (single-digit Mbps from EU datacenters) exactly where workers may rent. GHCR remains in place for small images.
- Managed cloud registries (Google Artifact Registry ~$4.80, Azure ~$3.48 per 40 GB pull). Rejected — per-pull download cost scales with success (~$350–480/mo at 100 pulls) against R2's $0.
- Split-and-join of oversized files to stay under GHCR's cap. Rejected — permanent chunking machinery in the build plus 1–3 minutes at every worker start, and the EU tail remains.
- Ship fp8-only or fp16-only. Rejected for launch — fp8 carries a documented open seam defect (RoPE quantization), fp16 pays the 1.5–2× block-swap slowdown on 24 GB cards; shipping both keeps the choice a preset/config matter until our own A/B decides.
