# Provisioner and worker-pool lifecycle

Details the pool that ADR 0014 made primary. Workers live as rows in a `workers` table with a stored state — `Provisioning` (instance created or being re-imaged; container starting, image downloading), `Preparing` (agent answering; readiness gate running), `Ready`, `Processing` (exactly one job attempt), `Updating` (in-place agent-binary swap), `Destroyed` (terminal; row kept as history) — reusing the job side's state-timeout and recovery-check pattern. Lifecycle decisions and claims are durable database facts; live health is never read from storage (heartbeats and probes carry it). Dispatch takes a worker by an atomic claim (flip to `Processing` only if still `Ready` and current-image); the updater claims through the same gate, so nothing can grab a worker mid-update. Every destruction goes through one shared idempotent routine (set `Destroyed` + reason; retry Vast's destroy until confirmed). Death reasons are data: `ProvisioningTimeout`, `InstanceFailure`, `PreparationFailed`, `Surplus`, `ScaledDown`, `ReplacedWithBetterMachine`, `ReplacedWithNewerVersion`, `UpdateFailed`, `RecoveryFailed`, `HeartbeatLost` — the first three and last three write the machine into the bad-machine memory, the middle four do not. Vast's own `actual_status` rides on the row as auxiliary data; its documented terminal values (`exited`/`unknown`/`offline`, or "Error" in `status_msg`) kill a worker immediately in any state.

Admission is the readiness gate alone — ComfyUI answering, model files visible, free-VRAM fraction, empty queue (the POC's live-proven checks, run on-box by the agent). There is no compute test: POC experience shows a machine that downloads and sets up always runs jobs, and same-GPU speed spread (~1.5×) never justifies discarding a provisioned machine. Machine speed is instead predicted: every worker row captures the machine's hardware fingerprint (GPU/CPU/RAM/disk/PCIe — the fields the POC already records in ETA traces), every job ties its duration to that fingerprint, and accumulated history scores machines. `Preparing` is patient — "still starting" responses poll on, a VRAM latch triggers the agent's ComfyUI restart — and `PreparationFailed` fires only when the deadline lapses with remedies exhausted. During `Provisioning` the backend parses download progress from the instance logs: the ~2-minute signs-of-life checkpoint, projection-based early kills (current rate extrapolated past the image-size-aware boot deadline), stall-vs-slow discrimination, and a measured delivery rate for the ledger (deadlines remain the backstop if log parsing proves unreliable).

The permanent `machines` ledger (keyed by Vast `machine_id`, outliving any rental) accumulates fingerprints, measured download/boot rates, job outcomes, and one continuously recomputed quality score (no manual-override column; a hand edit would be overwritten). Renting prefers known machines by score; strangers are raced: rent the N cheapest qualifying offers (allowed GPU models, disk floor, ~1 Gbit download floor, price cap, reliability floor, CUDA floor, no geography filter, banned machines excluded), first to pass wins, the rest die as `Surplus` from whatever state they reached — no bad mark, scores and warm caches retained. Bad-machine bans escalate linearly (14 days, +7 per repeat offense) and reset to the 14-day base once a machine redeems itself after a ban; the search simply excludes unexpired bans, and a host accumulating entries raises an alert for a manual host exclusion. A quiet-time, budget-capped scouting pass keeps the ledger alive: it re-tests known machines with stale scores and samples the untried cheap segment, replacing the worst below-excellent floor machine when a candidate beats it by a configured margin; its intensity derives from pool configuration (scales with the warm floor) with manual override. When no offer qualifies, filters never relax automatically — an immediate highest-severity alert fires while the provisioner keeps retrying, and manually rented instances are a supported response: a periodic reconciliation pass (account instance list vs the table) adopts unknown instances running our image into `Provisioning` — unknown heartbeats are ignored, adoption's only path is reconcile — and flags anything else without touching it.

Updates are two-tier. Agent-only releases hot-swap the single-file binary through `Updating` (presigned download, checksum, restart, report in; ~2-minute timeout into the escalation ladder; staggered one floor worker at a time). Image releases re-image instances in place via Vast's `update_template` + `recycle` (container recreated from the new image without losing the machine; cached byte-stable layers make it a delta pull), driven by pure tag comparison — no stored retirement marker: the claim query prefers current-tag workers, a stale worker goes from job-end into its re-image turn, and the floor count ignores stale workers so replacements happen one at a time, stale workers staying claimable until their turn. Destroy-and-re-rent by `machine_id` filter is the fallback (racy; no documented reappearance delay). Dispatch finding no free worker triggers the provisioner directly rather than waiting for its timer; the pre-delivery health probe runs only on workers idle past ~30 minutes; Jupyter stays exposed on the worker image as a debugging hatch (user decision, risk noted).

## Considered Options

- Pool state in the provisioner's memory with Vast as truth. Rejected — restarts forget admissions and claims, nothing serializes two dispatchers grabbing one worker, and the ledger needs durable rows anyway.
- A timed mini-render as an admission gate (ADR 0014's original shape). Dropped — contradicted by POC experience (gate-passing machines always worked); fingerprint + job-history prediction replaces measurement, and an idle-time test render stays available as a post-v1 scouting refinement.
- A `Retiring` state, then a retirement flag. Both rejected — states describe activity, plans are data, and the image-tag comparison needs no storage at all.
- Automatic filter relaxation during droughts. Rejected — spend and quality must not drift without a human; immediate alert instead.
- Permanent bad-machine bans. Rejected — stale evidence shrinks the market forever; escalating expiring bans self-clean.
- Rollout by destroy-and-re-rent (ADR 0015's original turnover). Superseded by in-place update+recycle — destroying releases the machine to the open market and a competitor can take it.
