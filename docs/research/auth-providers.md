# Authentication options survey

Wayfinder research. Survey only — the auth decision belongs to its own ticket.

**Question**: how should the C#/.NET 9 backend (K3s single node on Hetzner, PostgreSQL via CloudNativePG, Cloudflare at the edge) authenticate its future SPA frontend and REST API? Candidates: ASP.NET Core Identity inside the existing API deployable, a hosted auth provider, or a self-hosted identity server. Side question: transactional email for verification/password-reset mails at tiny volume. Audience: cost-sensitive solo operator, 10–100 users at launch, seams to low 1000s.

All prices USD, verified against primary sources 2026-09-21. One JS-rendered pricing page (Brevo) could not be scraped and is flagged inline.

## 1. ASP.NET Core Identity in .NET 9

1. **Out of the box**: "Manages users, passwords, profile data, roles, claims, tokens, email confirmation, and more"; external login providers (Google, Facebook, Microsoft Account, Twitter via the social-auth handlers), MFA/2FA with authenticator apps, password management, and account lockout with configurable policy (`Lockout.DefaultLockoutTimeSpan`, `MaxFailedAccessAttempts`, `AllowedForNewUsers`) (https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity?view=aspnetcore-9.0, https://learn.microsoft.com/en-us/aspnet/core/security/authentication/social/). Password hashing is the built-in `PasswordHasher` (PBKDF2; V3 format is HMAC-SHA512) (https://github.com/dotnet/aspnetcore/blob/main/src/Identity/Extensions.Core/src/PasswordHasher.cs). Email-confirmation and password-reset **tokens** are generated by the framework (`GenerateEmailConfirmationTokenAsync` etc.); .NET 9+ also ships Identity metrics for sign-in observability. Microsoft's own selection guide: "For most scenarios, this may be the only provider needed" (https://learn.microsoft.com/en-us/aspnet/core/security/how-to-choose-identity-solution?view=aspnetcore-9.0).
2. **`MapIdentityApi<TUser>` (since .NET 8)** adds ready-made API endpoints: `POST /register`, `POST /login`, `POST /refresh`, `GET /confirmEmail`, `POST /resendConfirmationEmail`, `POST /forgotPassword`, `POST /resetPassword`, `POST /manage/2fa`, `GET|POST /manage/info` (https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-9.0). Two modes per login call via `useCookies`: cookie auth, or a proprietary bearer access token + refresh token.
3. **Token-mode caveats, verbatim from the doc**: "The tokens aren't standard JSON Web Tokens (JWTs). The use of custom tokens is intentional, as the built-in Identity API is meant primarily for simple scenarios. The token option isn't intended to be a full-featured identity service provider or token server, but instead an alternative to the cookie option for clients that can't use cookies." And the SPA guidance: "We recommend using cookies for browser-based applications, because, by default, the browser automatically handles them without exposing them to JavaScript." The refresh endpoint exists (`BearerTokenOptions.RefreshTokenExpiration` controls lifetime) but there is no documented rotation/revocation-family machinery; after a security-sensitive change, a bearer session only dies when the access token expires (security stamp is re-checked per `BearerTokenExpiration`), whereas cookies revalidate on `SecurityStampValidatorOptions.ValidationInterval` (same doc). The selection guide adds that the Identity-issued token "Isn't suitable for managing access from third-party apps" (https://learn.microsoft.com/en-us/aspnet/core/security/how-to-choose-identity-solution?view=aspnetcore-9.0).
4. **Not provided**: email sending — you must register an `IEmailSender` implementation yourself (the doc's `EmailSender` stub) and set `RequireConfirmedEmail`; no hosted login pages (the default Razor UI targets server-rendered apps, not the API endpoints); **no `/logout` endpoint and no external/social-login endpoints in `MapIdentityApi`** — social login is wired separately through the cookie-based external auth handlers; no admin UI; no OIDC issuance for third-party clients (https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-9.0).
5. **PostgreSQL fit**: Identity persists through `Microsoft.AspNetCore.Identity.EntityFrameworkCore` over any EF Core provider — docs note SQL Server is merely the typical default and "another persistent store can be used" (https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity?view=aspnetcore-9.0). With the open-source Npgsql EF Core provider the Identity tables are ordinary EF migrations on the existing CloudNativePG database (https://www.npgsql.org/efcore/). No new deployable, no new backup surface.

## 2. Hosted auth providers

1. **Auth0**: Free plan **25,000 MAU**, unlimited social connections, **1 custom domain included**, but no MFA on free; first paid tier Essentials "from $35/month" (B2C, at 500 MAU — the paid tiers price by MAU band, so growing past free is a step change) (https://auth0.com/pricing). EU residency: tenant region is chosen at creation — EU region runs from Frankfurt/Dublin and is selectable on free accounts (https://auth0.com/platform/cloud-deployment, https://support.auth0.com/center/s/article/Tenant-Creation-in-a-Specific-Sub-region). Integration: standard OIDC — the API validates real JWTs with `AddJwtBearer` (Authority = tenant domain, Audience = API identifier) per the official ASP.NET Core quickstart (https://auth0.com/docs/quickstart/backend/aspnet-core-webapi).
2. **Clerk**: Free Hobby plan **50,000 MRU** — note the metric: monthly *retained* users; "a user only counts as retained if they return to your app at least 24 hours after signing up", which is materially more generous than MAU. Up to 3 social providers and a custom domain on free; Pro is **$25/mo** ($0.02 per MRU beyond 50k) and gates MFA, passkeys, custom email templates, custom password rules, and branding removal (https://clerk.com/pricing). **No EU data residency** — infrastructure and all subprocessors are US-based, relying on the Data Privacy Framework (https://clerk.com/security, https://clerk.com/legal/dpa). Integration: Clerk-issued JWTs verified via JWKS; official C# backend SDK `Clerk.BackendAPI` with an `AuthenticateRequest` helper for ASP.NET (https://github.com/clerk/clerk-sdk-csharp, https://clerk.com/changelog/2025-01-09-csharp-sdk). Clerk is SPA-component-first — its strength is the prebuilt React UI.
3. **Supabase Auth**: "You can use Supabase Auth as a standalone product" — but "Auth uses your project's Postgres database under the hood, storing user data and other Auth information in a special schema" (https://supabase.com/docs/guides/auth). Practically: hosted Supabase Auth means **auth users live in a Supabase-managed Postgres while app data stays on CloudNativePG** — two databases, which is fine, just explicit. Fully self-hosting only the Auth server against your own Postgres is possible but the stack expects Supabase-specific roles and extensions, and community consensus is that it is not worth it (https://github.com/orgs/supabase/discussions/6426, https://github.com/orgs/supabase/discussions/33843). Pricing: free tier **50,000 MAU** with social OAuth providers included; Pro $25/mo with 100,000 MAU then $0.00325/MAU; custom domain $10/mo on Pro+ (https://supabase.com/pricing). Project region (incl. EU) is picked at creation (https://supabase.com/docs/guides/platform/regions). Integration: since the 2025 JWT-signing-keys release, tokens can be signed asymmetrically and verified against the project JWKS endpoint (`https://<ref>.supabase.co/auth/v1/jwks`) — plain `AddJwtBearer`, no shared secret in the API (https://supabase.com/blog/jwt-signing-keys, https://supabase.com/docs/guides/auth/signing-keys).
4. **WorkOS AuthKit**: free for the **first 1,000,000 MAU**, then $2,500/mo per additional million; email+password, social login, passkeys, MFA, magic links, and enterprise SSO all included in the free band. Catch for a consumer-facing product: a **custom auth domain is a $99/mo add-on**, and enterprise SSO connections are $125 each (https://workos.com/pricing). Integration is standard OIDC/JWT.
5. **Firebase Authentication**: free **50,000 MAU** (Spark and within Blaze), 50 MAU for SAML/OIDC federation; beyond that, Google Cloud Identity Platform per-MAU pricing applies, and phone auth bills per SMS (https://firebase.google.com/pricing). Google-account-shaped ecosystem; JWT validation against Google's JWKS works from ASP.NET Core, but there is no first-party .NET-centric story.
6. **Stytch**: free **10,000 MAU** ("users and AI agents"), then pay-as-you-go; full auth feature suite and 5 SSO/SCIM connections included; brand removal/full email customization is a $99 add-on (https://stytch.com/pricing).

## 3. Self-hosted identity servers

1. **Keycloak**: full OIDC server with hosted login pages, admin console, and social identity brokering; runs on Kubernetes via official containers/Operator with PostgreSQL. Documented sizing: base memory ~**1,250 MB per pod** (realm caches + 10,000 cached sessions), ~300 MB non-heap, heap sized to 70% of the container limit (https://www.keycloak.org/high-availability/multi-cluster/concepts-memory-and-cpu-sizing). Release cadence after 26.0: **4 minor releases per year, a major every 2–3 years**, with community fixes effectively only on the latest stream (https://www.keycloak.org/2024/10/release-updates, https://endoflife.date/keycloak). On a single small Hetzner node that is a JVM service the size of the whole rest of the stack, plus a quarterly upgrade treadmill.
2. **Zitadel**: Go-based, notably lighter — "ZITADEL itself requires approximately 512MB of RAM and can operate with less than one CPU core", though it wants CPU headroom for password-hashing spikes; PostgreSQL is the (only) supported database since v3 standardized on it (https://zitadel.com/docs/self-hosting/manage/production). **License changed from Apache 2.0 to AGPL-3.0 with v3 (2025-03-31)** for the core/console/hosted-login; APIs, SDKs, Helm chart and docs stay Apache 2.0 — self-hosting an unmodified Zitadel remains free and permissible (https://zitadel.com/blog/apache-to-agpl, https://github.com/zitadel/zitadel/releases/tag/v3.0.0, https://help.zitadel.com/zitadel-licensing-faqs).
3. **Duende IdentityServer**: a .NET library that runs inside your own ASP.NET Core app rather than a separate product — the lightest operationally of the three. Licensing today: **Community Edition is free for production** for for-profits with "less than $1M USD projected annual gross revenue and access to less than $3M USD in capital" (non-profits: budget under $1M), is "mostly feature-equivalent to the Standard Edition", and does not expire while eligible (https://duendesoftware.com/products/communityedition). The old $1,500/yr Starter tier is gone: paid tiers are now **Lite $5,750/yr** (1 deployment, 2 client IDs), Standard $12,500/yr, Advanced $24,900/yr (https://duendesoftware.com/pricing). Development/testing needs no license at all (https://duendesoftware.com/products/identityserver).
4. **Do they earn their keep at 10–100 users?** No — not when the alternative is Identity inside the already-deployed API. All three exist to be an *OIDC token server*: single sign-on across multiple apps, third-party API clients, standard JWTs for many audiences. Microsoft's guidance draws exactly this line: "For apps that don't share logins with other apps, the simplest way to quickly secure an app is to use the built-in ASP.NET Core Identity provider" (https://learn.microsoft.com/en-us/aspnet/core/security/how-to-choose-identity-solution?view=aspnetcore-9.0). This backend has one SPA and one API. Keycloak would be the single heaviest pod on the node; Zitadel is lighter but still a stateful service with its own upgrade, backup, and theming surface; Duende CE is free and in-process but still means operating a token server and tracking license eligibility. The one future that changes this answer is third-party API clients or a second product sharing logins — at which point Duende CE (free under $1M revenue, no re-platforming of user data since it sits on top of ASP.NET Core Identity) is the natural upgrade path.

## 4. Transactional email

1. **Resend**: free **3,000 emails/mo (100/day cap)**; Pro $20/mo for 50,000 (https://resend.com/pricing). Official .NET SDK (`Resend` on NuGet) (https://github.com/resend/resend-dotnet, https://resend.com/docs/send-with-dotnet); SMTP relay also available (https://resend.com/docs/send-with-smtp).
2. **Postmark**: free developer plan **100 emails/mo** (no expiry); Basic $15/mo for 10,000, $1.80/1,000 overage (https://postmarkapp.com/pricing). Transactional-deliverability specialist; official .NET library (https://github.com/ActiveCampaign/postmark-dotnet) plus SMTP.
3. **Amazon SES**: à la carte **$0.10 per 1,000 emails** — verification volume for 100 users rounds to $0; new AWS accounts get $200 in 6-month free-tier credits applicable to SES (https://aws.amazon.com/ses/pricing/). Caveats: accounts start in a sandbox and must request production access with a use-case justification (https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html), and the console/tooling is the usual AWS ceremony. .NET: `AWSSDK.SimpleEmailV2` or the SES SMTP interface.
4. **Brevo**: free plan **300 emails/day** forever; paid Starter from $9/mo for 5,000 emails (pricing page is JS-rendered — figures via Brevo's help center and 2026 secondary trackers: https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans, https://www.emailtooltester.com/en/reviews/brevo/pricing/). SMTP included on free.
5. **Mailgun**: free tier **100 emails/day**; Basic $15/mo for 10,000 (https://www.mailgun.com/pricing/).
6. **Cross-cutting**: deliverability setup is the same one-time task everywhere — SPF, DKIM, and DMARC DNS records on the sending domain, a few records in the already-present Cloudflare DNS zone, verified once in the provider dashboard. On the .NET side, `System.Net.Mail.SmtpClient` is explicitly not recommended: "We don't recommend that you use the SmtpClient class for new development... Use MailKit or other libraries instead" (https://learn.microsoft.com/en-us/dotnet/api/system.net.mail.smtpclient) — so plain-SMTP paths should go through MailKit, and HTTP-API SDKs avoid SMTP entirely.

## Assessment

For this operator — solo, cost-sensitive, one SPA + one API, users in the tens — **ASP.NET Core Identity inside the existing API deployable is the default answer**, and Microsoft's own decision guide says as much. It costs $0, adds zero pods to the single-node K3s cluster, stores users as ordinary EF-migrated tables in the CloudNativePG database already being backed up, and covers password hashing, lockout, confirmation/reset tokens, 2FA, and Google login via the stock auth handlers. For the SPA, use **cookie mode** (the documented recommendation for browser clients) rather than the proprietary bearer tokens, which are explicitly not JWTs and not a token server. The two things Identity genuinely does not do — send email and render login UI — are covered by one transactional-email provider plus the SPA's own login form. What is being given up: hosted login pages, an admin UI, and standard JWTs for third parties — none needed today.

Email: **Resend free tier (3,000/mo, official .NET SDK)** is the convenience pick at this volume; **Amazon SES ($0.10/1,000)** is the cheapest long-run floor if the AWS sandbox-exit ceremony is acceptable; Brevo's 300/day free tier is the fallback with the loosest cap. Either way the DNS records (SPF/DKIM/DMARC in Cloudflare) are a one-time task.

If the requirement instead becomes "write no auth code at all", the hosted free tiers are all comfortably larger than the launch scale: **Auth0 (25k MAU, EU tenant, real OIDC/JWT — the smoothest ASP.NET Core fit)** or **Supabase Auth (50k MAU, JWKS-verified JWTs, but auth users live in Supabase's Postgres, not the CloudNativePG one)**. Clerk's free tier is generous and its React components are excellent, but it is US-only for data residency and its .NET story is secondary. WorkOS's 1M free MAU is striking but the $99/mo custom-domain add-on undercuts it for a consumer product.

Self-hosted identity servers are not warranted at this scale: Keycloak's ~1.25 GB baseline and quarterly release stream is a poor trade on a single small node, and even lightweight Zitadel (~512 MB, AGPL since v3) is a whole extra stateful service. The seam to keep in mind is **Duende IdentityServer Community Edition** — free in production under $1M revenue, layered on top of the same ASP.NET Core Identity user store — as the no-re-platforming upgrade path if third-party API clients or cross-app SSO ever materialize.

## Addendum (2026-09-21): provider-bundled extras — bot protection, e-mails, admin dashboard

Follow-up fact-check against primary sources, same day. Focus: what Clerk bundles that ASP.NET Core Identity would leave the operator to assemble, plus the matching Auth0/Supabase comparison points.

### Clerk

1. **Bot protection on sign-up — included on every plan, Cloudflare Turnstile under the hood.** The pricing feature table lists "Bot protection" (plus account lockout / brute-force protection and disposable-email blocking) on both the free Hobby plan and Pro (https://clerk.com/pricing). Mechanism: Clerk "leverage[s] data from our CDN to determine whether a user attempting to sign up might be a bot", and shows an interactive challenge only to suspected bots ("Smart" CAPTCHA type by default); the widget is Cloudflare Turnstile (the docs note some Clerk-supported languages "are not supported by Cloudflare Turnstile, which is used for the CAPTCHA widget") (https://clerk.com/docs/guides/secure/bot-protection, https://clerk.com/docs/guides/development/custom-flows/authentication/bot-sign-up-protection). It is controlled by a "Bot sign-up protection" toggle on the Dashboard's attack-protection settings — the doc walks through enabling it rather than describing it as pre-enabled. Two caveats: a custom (non-Clerk-component) sign-up form must render a `<div id="clerk-captcha" />` placeholder, and enabling the "Native API" setting bypasses CAPTCHA for native apps/extensions (same docs).
2. **Auth e-mails — Clerk sends them itself; no transactional-mail account needed on any plan.** Clerk delivers verification/reset mails from its own infrastructure ("Clerk uses a pool of dedicated IP addresses to help maintain strong sender reputation"). Development instances send from `@accounts.dev`; **production instances send from your own domain** (the production-instance setup has you add SPF/DKIM DNS records, which "Clerk handles… for you automatically" once created; adding DMARC is a recommended manual TXT record) (https://clerk.com/docs/guides/development/troubleshooting/email-deliverability). Since a custom domain is included on the free plan (https://clerk.com/pricing), free-plan production mail already comes from your domain. What Pro ($25/mo) gates is **custom e-mail templates** and **removing Clerk branding** from the defaults (https://clerk.com/pricing).
3. **Admin capabilities in the Dashboard.** Free (Hobby): view/manage users, up to 3 dashboard seats, and **up to 5 user impersonations per month** (impersonation is also on free). Pro adds **user bans** and **allowlist/blocklist**; unlimited impersonation requires the Administration add-on at **$100/mo ($85/mo annual)** on top of Pro; **admin/audit logs only appear on the Business tier** (30-day retention) (https://clerk.com/pricing). Automatic account lockout after failed attempts (brute-force protection) is on all plans (https://clerk.com/pricing).
4. **Data residency — still US-only, unchanged.** The DPA states Clerk "hosts Personal Data primarily in Google Cloud data centers and Cloudflare" and relies on self-certification under the Data Privacy Framework for EEA/UK/Swiss transfers; no EU-region option is offered (https://clerk.com/legal/dpa, https://clerk.com/legal/gdpr).
5. **Separate C#/.NET REST API — the official pattern works, with a token-model quirk.** Clerk's session token is a **short-lived RS256 JWT (60-second lifetime)** that clerk-js refreshes automatically in the background; the SPA fetches a current token per request (`getToken()`) and sends it in the `Authorization` header for cross-origin calls (https://clerk.com/docs/guides/how-clerk-works/overview, https://clerk.com/docs/guides/sessions/manual-jwt-verification). The API verifies it against the instance JWKS (`<Frontend API URL>/.well-known/jwks.json` or `https://api.clerk.com/v1/jwks`) — i.e. plain `AddJwtBearer` with RS256 + `azp` origin check works, or the official C# SDK `Clerk.BackendAPI` with `AuthenticateRequestAsync` (networkless when given the instance's PEM public key) (https://clerk.com/docs/guides/sessions/manual-jwt-verification, https://github.com/clerk/clerk-sdk-csharp). **Session length**: the long-lived session behind those tokens defaults to a *fixed 7-day maximum lifetime* on free; a ~30-day sliding session means setting inactivity timeout and/or maximum lifetime, and "setting a custom maximum lifetime requires a paid plan for production use" (same for inactivity timeout) — i.e. **Pro is required for 30-day sessions** (https://clerk.com/docs/guides/secure/session-options, https://clerk.com/pricing). One account signed in from several devices is normal (each device holds its own session); the pricing-page "simultaneous sessions" Pro feature is the *multi-session* capability — several *accounts* signed in from one browser (https://clerk.com/docs/guides/secure/session-options, https://clerk.com/pricing).
6. **Mirroring users into your own Postgres — webhooks, explicitly documented.** The official sync guide subscribes to **`user.created`, `user.updated`, `user.deleted`** and writes to your DB from the handler. Delivery runs on Svix: verify each delivery with the signing secret, return 2xx to acknowledge; non-2xx (or >15 s without a response) triggers automatic retries with exponential backoff. The docs' own reliability framing: sync is "eventually consistent", and "webhook deliveries are not guaranteed and may occasionally fail… your implementation should be prepared to handle retries and error scenarios" — so handlers must be idempotent (the `svix-id` header serves as the dedup key) (https://clerk.com/docs/guides/development/webhooks/syncing, https://clerk.com/docs/guides/development/webhooks/overview).

### Comparison points

1. **Auth0 — bot detection is effectively enterprise-only, and auth e-mail needs your own provider.** The pricing feature table has brute-force protection and suspicious-IP throttling on all plans including Free, but **Bot Detection is not available on Free, Essentials, or Professional — it is an Enterprise add-on** (breached-password detection starts at Professional, $240/mo) (https://auth0.com/pricing, https://auth0.com/docs/secure/attack-protection/bot-detection). E-mail: the built-in provider is for development only — all mail comes from `no-reply@auth0user.net`, capped at **10 e-mails/minute**, no custom templates or From address — "you must configure an external SMTP email provider" for production (https://auth0.com/docs/customize/email, https://auth0.com/docs/customize/email/smtp-email-providers). So the "no transactional-mail service" saving Clerk offers does **not** apply to Auth0: its free 25k MAU still needs Resend/SES/etc. behind it.
2. **Supabase Auth — CAPTCHA built-in, but production e-mail needs custom SMTP.** CAPTCHA: first-party support for **hCaptcha and Cloudflare Turnstile** — pick the provider and paste the secret key in the Dashboard, render the widget in the frontend (https://supabase.com/docs/guides/auth/auth-captcha). E-mail: Supabase does send auth mails itself, but the default service is explicitly not production-grade — **2 messages/hour**, delivery **only to project team-member addresses**, "no SLA guarantee on message delivery or uptime"; the docs urge a custom SMTP provider for everything beyond exploration (which starts you at 30 msgs/hour, adjustable) (https://supabase.com/docs/guides/auth/auth-smtp).

### What this changes for the assessment

Clerk's bundle is materially larger than the earlier survey credited: on the **free plan** it covers Turnstile-backed bot protection, production auth e-mail from your own domain with no mail provider, brute-force lockout, a user-management dashboard with 5 impersonations/month, and JWKS-verified JWTs a .NET API consumes with stock `AddJwtBearer`. The Identity-in-API path needs the operator to assemble each of those (Turnstile wiring, a mail provider + SPF/DKIM, lockout config is built-in, admin UI is absent). The real Clerk costs for this project are: **US-only data residency** (unchanged, and the survey's main objection stands), **Pro ($25/mo) as soon as a ~30-day session is wanted** (free is fixed at 7 days), user bans also being Pro, and the eventual-consistency/webhook-idempotency machinery for mirroring users into the CloudNativePG database. Auth0's free tier, by contrast, bundles *neither* bot detection (enterprise add-on) *nor* production e-mail (own provider required), which weakens it as the "write no auth code" pick; Supabase sits in between (CAPTCHA free, e-mail needs your own SMTP account — the same mail-provider task as the Identity path).

## Addendum (2026-09-21): Clerk availability track record

Same-day follow-up on the "Clerk being reachable" worry: incident history mid-2025 → 2026-09-21, from Clerk's own status page and postmortems, then community reports, then the blast-radius question (what happens to already-signed-in users when Clerk is down, given the 60-second session JWTs).

Sources note: Clerk's status page (https://status.clerk.com/, hosted on incident.io) only *displays* the trailing **90 days** — older incidents stay reachable at their direct URLs and via the published postmortems, but there is no browsable long-term archive, and its incident data only begins 2025-02-27 (the incident.io migration date, per the page's own API metadata). Everything below older than 90 days was reconstructed from direct incident URLs, Clerk's postmortem blog, and third-party monitors, and is labelled accordingly.

### Official record: significant incidents, mid-2025 → Sep 2026

1. **2025-06-26 — full outage of all Clerk services, 45 minutes** (06:16–07:01 UTC). Google Cloud Run Direct VPC workloads in us-central1 went into a restart loop; Clerk was single-region, so everything — authentication, session management, dashboard — was down. Clerk announced it on X and published a postmortem admitting the architectural gap: "a single-region architecture, even with AZ redundancy, is still vulnerable to full regional outages" (https://clerk.com/blog/postmortem-jun-26-2025-service-outage, https://x.com/ClerkDev/status/1938127848931467697).
2. **2025-08-06 — regional-failover debut, ~101 minutes of provider trouble, minimal impact.** Clerk shipped cross-region failover on 2025-08-04 (a direct remediation of the June incident); two days later the primary region flapped for ~1h40m and the failover absorbed it — "From a customer perspective, there was no noticeable disruption. Aside from a few early errors, which were automatically retried by our SDKs" (https://clerk.com/blog/resilience-in-practice-regional-failover).
3. **2025-09-15 → 09-18 — database degradation, ~3.75 days of intermittent impact; the window's longest incident.** A cloud-provider auto-upgrade of Postgres plus Clerk's synchronized 15-minute connection recycling caused a recurring "thundering herd": "intermittently impacted customer traffic with significant request failures and latency spikes" from Sep 15 13:08 UTC until the root-cause fix Sep 18 03:19 UTC. Notable split: "session management was functional due to the session endpoints higher tolerance for latency, as well as the retry mechanism in our SDKs", while new sign-ins/sign-ups failed in bursts (worst burst 3–6 minutes) (https://clerk.com/blog/2025-09-18-database-incident-postmortem, https://status.clerk.com/incidents/01K56S4WM182X7GH5YQV08DSQ7).
4. **2025-10-10/11 — sign-in failures for a subset, ~10 hours 50 minutes** (Oct 10 20:00 → Oct 11 06:50 UTC). ### Uptime figures and SLA

1. **No trailing-12-month uptime number is published.** The status page shows per-component uptime bars over the visible 90 days only — on 2026-09-21 every component reads ~100% except the dashboard's "Go live" component at 99.84% (https://status.clerk.com/). The Feb/Mar 2026 full outages have already scrolled out of that window.
2. **SLA: Enterprise only.** The pricing page lists "99.99% Uptime SLA" solely under Enterprise (custom, annual); Hobby, Pro, and Business carry **no contractual availability commitment** (https://clerk.com/pricing).
3. Napkin math on the record above: the three hard full-outage windows inside the last 12 months (Dec 5 ≈ 25 min, Feb 19 ≈ 90 min, Mar 10 ≈ 26 min) alone total ≈ 2.4 hours ≈ **99.97% availability of token issuance over the year** — before counting the degraded-service episodes (Sep 2025's 3.75 intermittent days, Feb 10's DNS partial). Roughly "three nines in practice, four nines promised only to Enterprise".

### Community reports vs the status page

1. **No evidence of hidden outages.** Hacker News has no front-page Clerk-outage thread in the window (Algolia searches for "clerk outage" / "clerk is down" return only irrelevant hits); Reddit searches likewise surfaced no dated thread contradicting the status page. The Feb 19, 2026 outage produced downdetector-style user reports "surging around 11:17 AM Eastern" (= 16:17 UTC, matching Clerk's 16:11 start) and an "Is Clerk down?" forum thread the same day (https://community.designtaxi.com/topic/23797-is-clerk-down-february-19-2026/) — community timing *corroborates* the status page rather than undercutting it.
2. **Where Clerk itself admits understatement:** the Mar 10 postmortem notes internal 429s were not being transformed to 500s, skewing "accurate status assessment" (they now fix this), and the Feb 19 postmortem's remediations include "incident communication improvements" with dedicated comms leads — i.e. status updates during the worst incident were acknowledged as too slow, but not false (https://clerk.com/blog/2026-03-10-service-outage-postmortem, https://clerk.com/blog/2026-02-19-system-outage-postmortem).
3. **Volume caveat on third-party counters:** StatusGator counts "171 outages since March 2025" (https://statusgator.com/services/clerk) — that tallies every status-page event including minor single-component blips and maintenance, not user-facing auth downtime; a third-party probe put 30-day uptime at 99.39% in September 2026 under its own degraded-counting rules (https://apistatuscheck.com/api/clerk). Treat both as noisier than the incident-by-incident record above.

### The 60-second-JWT blast radius: do signed-in users survive a Clerk outage?

1. **Mechanism**: the session token is a 60-second JWT that clerk-js re-fetches from Clerk's Frontend API on a ~50-second cycle; your API verifies it locally against cached JWKS keys, so *verification* needs no live Clerk call — but *re-issuance* does (https://clerk.com/docs/guides/how-clerk-works/overview).
2. **Baseline answer: everyone is kicked out within about a minute.** If token issuance is down, existing users' JWTs expire in ≤60 s and every authenticated request starts failing; Clerk's own June 2025 postmortem says it plainly: "Any incident in our Session Management service has an outsized impact on our customers, since it results in complete downtime of their service" (https://clerk.com/blog/postmortem-jun-26-2025-service-outage). The blast radius of a full Clerk outage is **not** "new sign-ins fail" — it is "the whole app is down for everyone" (for API-verifying backends like the planned .NET one, until token issuance returns).
3. **What Clerk built since** (all inside the window): cross-region failover (Aug 2025), plus a dedicated session-token failover / "Origin Outage Mode" that keeps *issuing* session tokens through a separate path when the core API fails (https://clerk.com/blog/resilience-in-practice-regional-failover, https://clerk.com/blog/2026-02-19-system-outage-postmortem, https://clerk.com/blog/2026-03-10-service-outage-postmortem). Track record of that mitigation: Sep 2025 — sessions rode out a multi-day degradation while sign-ins broke in bursts; Feb 19, 2026 — sessions were down ~57 minutes until the failover was *manually* switched on; Mar 10, 2026 — it auto-triggered, stumbled (429s), and was effective from minute ~13 of 26. So: materially better than the naive 60-second cliff, but demonstrated as best-effort, not a guarantee — signed-in users have still been locked out for tens of minutes twice in 2026.

### What this changes for the assessment

The reliability record is neither a disqualifier nor reassuring enough to ignore. Over the last 12 months Clerk had **three short full outages (25, ~90, and 26 minutes) plus one multi-day intermittent degradation and one partial DNS outage**, several traced to the same soft spot (managed Postgres under provider-initiated changes), each followed by an unusually candid postmortem and structural fixes (regional failover, session-token failover, DNS failover in progress) — and the most recent quarter is clean. The decision-relevant asymmetry stands: with Clerk, a Clerk outage takes the whole product down for *everyone within a minute* (minus the not-yet-fully-proven Origin Outage Mode), and the free/Pro tiers carry no SLA; with ASP.NET Core Identity in-process, auth is exactly as available as the API itself — there is no separate party to be "reachable". If Clerk is chosen anyway, two cheap hedges follow from the record: verify JWTs against *cached* JWKS with a generous refresh window (verification then survives Clerk blips; only issuance is exposed), and treat 4xx/5xx from token refresh as "retry with backoff", which is exactly what rode out the September 2025 degradation.
