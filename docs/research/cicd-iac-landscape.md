# CI/CD and IaC landscape for the SeedVR2 backend (2026)

Date: 2026-09-15. Scope: public GitHub monorepo, .NET backend deployed via GitHub Actions + Helm 4 to a single Hetzner K3s box (CloudNativePG, no Flux), R2 + B2 storage, Vast.ai GPU workers pulling a 15–30 GB image, Cloudflare edge.

**TL;DR.** OpenTofu is the safest IaC pick: every provider we need (hcloud, cloudflare, b2, github) is on its registry at identical versions to Terraform's, it adds client-side state encryption, and its `skip_s3_checksum` also disables the AWS-SDK integrity checks that still break third-party S3 stores in Terraform. R2 works as the state backend including S3-native `.tflock` locking — R2 has supported `If-None-Match` conditional PUT since 2022 — though "locking works on R2" end-to-end is only third-party-confirmed. Vast.ai has no dependable IaC provider in any ecosystem; drive templates/serverless endpoints via its REST API/CLI. GHCR is the registry: free for public images, no published pull-rate limits (Docker Hub's 100 anonymous pulls/6 h per IPv4 is a hazard on shared Vast host IPs), with one hard rule — no layer over 10 GB. Public repos get unlimited free minutes on the 4-core ubuntu-latest runner (~50–60 GB after cleanup actions); larger runners are always paid and need a Team/Enterprise org, so at the 30 GB image end a Hetzner self-hosted runner locked to trusted-branch workflows is the fallback. Deploy access: SSH tunnel (or Tailscale's official action) with a namespace-scoped ServiceAccount-token kubeconfig — never the k3s.yaml admin file, whose embedded cert silently expires within 12 months. Secrets: SOPS + age in git (helm-secrets v4.7+ supports Helm 4) has the best solo disaster-recovery story.

## 1. IaC tool choice — Terraform vs OpenTofu vs Pulumi

- **Terraform (BUSL 1.1)**: v1.16.2 as of 2026-09-09 ([releases](https://github.com/hashicorp/terraform/releases)). BUSL only forbids offering Terraform itself hosted/embedded to compete with HashiCorp/IBM products; internal use incl. own CI is explicitly fine ([HashiCorp FAQ](https://www.hashicorp.com/en/blog/hashicorp-updates-licensing-faq-based-on-community-questions)). IBM closed the acquisition 2025-02-27 ([TechCrunch](https://techcrunch.com/2025/02/27/ibm-closes-6-4b-hashicorp-acquisition/)). For a solo non-competing project the license is a practical non-issue.
- **OpenTofu**: v1.12.6 stable (2026-08-19), v1.13.0-beta1 out ([releases](https://github.com/opentofu/opentofu/releases)); Linux Foundation governance. Its registry mirrors ~4,000 providers ([blog](https://opentofu.org/blog/building-the-opentofu-registry/)); verified it carries hcloud 1.69.0 and b2 0.13.2 — identical to registry.terraform.io ([hcloud versions](https://registry.opentofu.org/v1/providers/hetznercloud/hcloud/versions), [b2 versions](https://registry.opentofu.org/v1/providers/backblaze/b2/versions)). OpenTofu-only features: native state encryption (1.7), static evaluation of backend config (1.8), `for_each` on providers (1.9). State compatible with Terraform up to the 1.5.x fork point; providers use the same protocol, so the divergence risk is mostly modules using post-fork Terraform-only syntax ([FAQ](https://opentofu.org/faq/)).
- **Pulumi (.NET)**: engine/CLI Apache 2.0 ([repo](https://github.com/pulumi/pulumi)); .NET SDK rated Stable, tested on .NET 8/9/10, Automation API included; known gap: policy packs can't be authored in .NET ([docs](https://www.pulumi.com/docs/iac/languages-sdks/dotnet/)). Backends: Pulumi Cloud free tier (1 user, unlimited resources) or DIY S3-compatible backend with `PULUMI_CONFIG_PASSPHRASE` secrets ([state docs](https://www.pulumi.com/docs/iac/concepts/state-and-backends/), [pricing](https://www.pulumi.com/pricing/)).
- **Providers**: hetznercloud/hcloud — partner tier, 18.8M downloads, v1.69.0 (2026-09-11), healthy ([registry](https://registry.terraform.io/providers/hetznercloud/hcloud/latest)). cloudflare/cloudflare — partner, 334M downloads, v5.25.0; the auto-generated v5 rewrite (GA Feb 2025) at its worst broke ~15% of resources ([status issue](https://github.com/cloudflare/terraform-provider-cloudflare/issues/5573)); Cloudflare targeted stability of the most-used resources by end of March 2026 with a v4→v5 migration tool ([changelog](https://developers.cloudflare.com/changelog/post/2026-01-20-terraform-v5.16.0-provider/)); no v6 exists, v4.x still patched, recurring v5 themes are state-upgrade/schema breakage. R2 coverage is now real: `cloudflare_r2_bucket` plus dedicated [lifecycle](https://developers.cloudflare.com/api/terraform/resources/r2/subresources/buckets/subresources/lifecycle/) and [CORS](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/r2_bucket_cors) resources. Backblaze/b2 — partner, v0.13.2 (2026-07-27), still 0.x but maintained; quirk: the Go binary embeds the B2 Python SDK ([repo](https://github.com/Backblaze/terraform-provider-b2)). integrations/github — partner, 372M downloads, v6.13.0 (2026-07-08), slowish cadence ([registry](https://registry.terraform.io/providers/integrations/github/latest)).
- **Vast.ai — no credible provider anywhere.** Official `vast-tools/Terraform_provider` is an unpublished toy, dormant since 2022 ([repo](https://github.com/vast-ai/vast-tools/tree/main/Terraform_provider)); community `aalekhpatel07/vastai` abandoned; `realnedsanders/vastai` (v0.3.1, templates+endpoints surface) was a single 4-day burst in Mar 2026 with an apply-time crash open ([repo](https://github.com/realnedsanders/terraform-provider-vastai), [issue](https://github.com/realnedsanders/terraform-provider-vastai/issues/5)). Use the REST API instead: base `https://console.vast.ai/api/v0`, Bearer auth, covering instances, templates, volumes, serverless endpoints, billing ([API intro](https://docs.vast.ai/api-reference/introduction)); templates via `POST /template` / `vastai create template` ([docs](https://docs.vast.ai/api-reference/templates/create-template)); serverless endpoints via `vastai create/update endpoint` with autoscaler params ([docs](https://docs.vast.ai/api-reference/serverless/create-endpoint)); CLI+SDK ship together as `pip install vastai` ([vast-cli](https://github.com/vast-ai/vast-cli)).
- **Pulumi packages**: bridged hcloud, cloudflare (v6.x tracks upstream v5 — inherits its bug surface) and github exist ([registry](https://www.pulumi.com/registry/packages/hcloud/)); no Pulumi b2 package — bridge it ad hoc via `pulumi package add terraform-provider backblaze/b2` ([Backblaze pointer](https://github.com/Backblaze/terraform-provider-b2/issues/2)).

## 2. State backend on R2

- S3-native locking (`use_lockfile = true`, a `.tflock` written with `If-None-Match`) landed in Terraform 1.10 ([changelog](https://github.com/hashicorp/terraform/blob/v1.10.0/CHANGELOG.md)) and OpenTofu 1.10 ([release blog](https://opentofu.org/blog/opentofu-1-10-0/)); DynamoDB locking is deprecated ([backend docs](https://developer.hashicorp.com/terraform/language/backend/s3)).
- R2 supports the required primitive: `If-Match`/`If-None-Match` (incl. `*`) on PutObject with 412 on conflict, documented since 2022 ([S3 API compat](https://developers.cloudflare.com/r2/api/s3/api/), [R2 changelog](https://developers.cloudflare.com/r2/platform/changelog/)). Contrast: Backblaze B2 returns 501 for the lock PUT — locking demonstrably fails there ([issue](https://github.com/hashicorp/terraform/issues/37143)). No primary source states "use_lockfile works on R2" end-to-end (Cloudflare's own guide omits locking); positive confirmations are third-party — mark that final step UNVERIFIED-by-primary-source.
- Config per Cloudflare's guide: `region = "auto"`, `skip_credentials_validation`, `skip_metadata_api_check`, `skip_region_validation`, `skip_requesting_account_id`, `skip_s3_checksum`, `use_path_style`, account-scoped endpoint ([remote backend guide](https://developers.cloudflare.com/terraform/advanced-topics/remote-backend/)). HashiCorp calls S3-compatible stores "best effort" only.
- Checksum saga: the Jan-2025 AWS SDK default-integrity change broke third-party stores; Terraform still has open issues where checksums leak past `skip_s3_checksum` ([#36704](https://github.com/hashicorp/terraform/issues/36704), [#37432](https://github.com/hashicorp/terraform/issues/37432); env-var workaround `AWS_REQUEST_CHECKSUM_CALCULATION=when_required`). OpenTofu 1.10 fixed this in core: its `skip_s3_checksum` also disables the SDK-level checks ([changelog](https://github.com/opentofu/opentofu/blob/v1.10.10/CHANGELOG.md)).
- OpenTofu state encryption is client-side and backend-agnostic (PBKDF2 passphrase, works over any backend incl. R2) ([docs](https://opentofu.org/docs/language/state/encryption/)).
- Pulumi: DIY backend supports S3-compatible endpoints via `pulumi login 's3://bucket?endpoint=...&s3ForcePathStyle=true'` ([docs](https://www.pulumi.com/docs/iac/operations/stack-management/using-a-diy-backend/)); R2 specifically is community-documented only (UNVERIFIED). Its locking is a lock-file-then-check scheme Pulumi itself calls "fundamentally limited by the non-transactional protocols of blob storage" — it does not use conditional writes ([state docs](https://www.pulumi.com/docs/iac/concepts/state-and-backends/)).

## 3. Container registry for the multi-GB worker image

- **GHCR**: public packages are free — no storage or egress charges ([billing docs](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-packages/about-billing-for-github-packages)). Hard limits: **10 GB per layer** and a 10-minute upload timeout ([container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)); a 25 GiB image worked once split into 7–8 GiB layers ([community discussion](https://github.com/orgs/community/discussions/77429)). No published anonymous pull-rate limit; community reports none in practice (absence UNVERIFIED — nothing official either way).
- **Docker Hub 2026**: enforced limits are 100 unauthenticated pulls per IPv4 (or IPv6 /64) per 6 h, 200 for free authenticated ([usage docs](https://docs.docker.com/docker-hub/usage/)); the harsher March-2025 limits were never enforced and storage billing is indefinitely delayed ([Docker blog](https://www.docker.com/blog/revisiting-docker-hub-policies-prioritizing-developer-experience/)). The per-IP quota is shared by every tenant on a Vast host's IP — the known failure mode for anonymous pulls from GPU marketplaces. No official Hub layer limit; ~10 GB/layer community figures are UNVERIFIED.
- **Vast.ai pulls**: templates take `registry/repo/image:tag` from any registry; private images via template "Docker Repository Authentication" (server name e.g. `ghcr.io`, username, password) or CLI `--login` ([template settings](https://docs.vast.ai/documentation/templates/template-settings)). Hosts opportunistically cache popular base layers ([vastai/base-image](https://github.com/vast-ai/base-image)); serverless counts a worker "running" only once the image is fully loaded, and its scaling knobs (cold workers etc.) exist because image load dominates cold starts ([serverless docs](https://docs.vast.ai/serverless)). No documented image-size limit or pull-through mirror — so keep model layers stable across releases so re-pulls fetch only changed layers, and build FROM a commonly cached base.
- **Self-hosted registry on R2**: distribution v3's S3 driver works with R2 (`regionendpoint` + `forcepathstyle`); the R2 equal-part-size multipart bug was fixed Nov 2024 ([PR](https://github.com/distribution/distribution/pull/4424)); AWS-SDK checksum compatibility against current R2 is UNVERIFIED — smoke-test a real 10 GB-layer push. zot also supports S3-compatible backends ([docs](https://zotregistry.dev/v2.0.1/articles/storage/)). Economics are compelling: R2 egress is free, a 30 GB image stores for ~$0.45/mo ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)) — but you run and secure the endpoint, and throughput is bounded by your VM. Sane fallback, not the default.

## 4. Building multi-GB images in CI

- **Standard runners**: ubuntu-latest is Ubuntu 24.04; public repos get 4 vCPU / 16 GB RAM / "14 GB SSD" ([runner docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)) — 14 GB is the guaranteed floor; real free space is ~21–29 GB on / plus a ~14 GB /mnt disk (community-measured, UNVERIFIED, drifts with image updates). Standard runners on public repos: **unlimited free minutes** ([billing docs](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
- **Larger runners are always paid**, even for public repos, and require a Team/Enterprise org ([billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [larger runners](https://docs.github.com/en/actions/reference/runners/larger-runners)). Sizes up to 64c; the 8c/32GB/300GB Linux x64 runner is $0.022/min ([pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)) ≈ $0.66 per 30-min build. What became free for public repos was the doubling of the *standard* runner to 4-vCPU ([blog](https://github.blog/news-insights/product-news/github-hosted-runners-double-the-power-for-open-source/)) plus free arm64 runners (Aug 2025).
- **Patterns**: jlumbroso/free-disk-space reclaims up to ~31 GB ([repo](https://github.com/jlumbroso/free-disk-space)); easimon/maximize-build-space additionally merges / and /mnt via LVM for roughly 50–60 GB usable ([repo](https://github.com/easimon/maximize-build-space)). Build with buildx docker-container driver and `--push` (no local image load). Cache: `type=gha` is capped by the Actions cache (default 10 GB/repo, raisable but extra storage is paid — [caching docs](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)) — useless for model layers; **`type=registry,mode=max` into GHCR is the right backend** ([docs](https://docs.docker.com/build/cache/backends/registry/)); `type=s3` (R2) is still experimental ([docs](https://docs.docker.com/build/cache/backends/s3/)). Order layers so models sit in early, stable layers; unchanged 10 GB layers are then cross-referenced, not re-uploaded.
- **Self-hosted runner**: sane once builds need >~60 GB or a persistent layer cache matters; a Hetzner CPX31-class VM (~€/mo in the mid-20s post-June-2026 price rise, UNVERIFIED exact figure) breaks even vs the 8c larger runner at ~19 build-hours/month and keeps its Docker cache between runs. **Security**: GitHub says self-hosted runners "should almost never be used for public repositories" — fork PRs can execute arbitrary code on them ([hardening guide](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). Mitigations: register the runner only for push/tag workflows on trusted branches (never fork `pull_request` triggers), use ephemeral/JIT runners, and set fork-PR approval to "all external contributors" ([repo settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)).

## 5. Deploying Helm from GHA to the K3s box

- **Kubeconfig secret against public 6443**: K3s API uses its own CA; the k3s.yaml admin credential is a client cert in `system:masters` — unrestricted ([cluster access docs](https://docs.k3s.io/cluster-access)). Allowlisting GitHub-hosted runner IPs is a non-starter: the `/meta` ranges are huge, weekly-updated, and GitHub explicitly recommends against using them as allowlists ([runner docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). If exposing 6443 at all, prefer a namespace-scoped ServiceAccount-token kubeconfig over the admin file (Kubernetes docs name CI/CD as the SA use case — [docs](https://kubernetes.io/docs/concepts/security/service-accounts/)); it is still a static bearer credential on a public port, and pre-auth kube-apiserver CVEs are the residual risk.
- **SSH tunnel**: firewall 6443 to localhost, workflow runs `ssh -N -L 6443:localhost:6443` then helm against `https://localhost:6443` (K3s certs include localhost SANs). Only port 22 exposed; needs an SSH key secret plus a pinned host key in `known_hosts`; the key is cluster-admin-by-proxy unless the kubeconfig used through it is scoped. Zero third-party dependencies; a little workflow plumbing.
- **Tailscale/WireGuard**: official `tailscale/github-action` v4 joins the tailnet as a tagged ephemeral node via OAuth client, auto-removed after the run ([action repo](https://github.com/tailscale/github-action)). Free Personal plan: 6 users, 50 tagged resources, **1,000 ephemeral-node minutes/month** — the binding constraint for CI, ample for short daily deploys ([pricing](https://tailscale.com/pricing)). API port never public; ACLs can restrict the CI tag to host:6443. Cost: dependency on Tailscale's coordination service at deploy time. Plain WireGuard avoids the third party (WG key as GH secret, `wg-quick up`) but is all-manual with no official action.
- **K3s specifics**: kubeconfig at `/etc/rancher/k3s/k3s.yaml`; add public IP/domain to the API cert with `--tls-san` ([server flags](https://docs.k3s.io/cli/server)). Client/server certs are valid 365 days and auto-renewed at startup when within 120 days of expiry ([certificate docs](https://docs.k3s.io/cli/certificate)); K3s rewrites k3s.yaml's inline certs on start and warns that copies must be manually refreshed — **a copied admin-kubeconfig GitHub secret silently dies within ≤12 months** ([cluster access](https://docs.k3s.io/cluster-access)). An SA-token kubeconfig avoids this. Helm 4 (released 2025-11-12) changes nothing about kubeconfig handling; CI-relevant deltas are plugin-only post-renderers and Server-Side Apply on upgrade; Helm 3 security fixes end 2026-11-11 ([Helm blog](https://helm.sh/blog/helm-4-released/)).

## 6. Secrets

- **GitHub environment secrets → helm upgrade**: environments are free on public repos ([docs](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)); secrets max 48 KB, 100 per environment, write-only with no export path ([limits](https://docs.github.com/en/actions/reference/security/secrets), [REST API](https://docs.github.com/en/rest/actions/secrets)). Fewest moving parts. DR: box loss is fine; repo or account loss destroys the (unreadable) secrets — GitHub is a cache, the source of truth must live in a password manager. Note `--set` values end up readable in the Helm release Secret on the cluster.
- **SOPS + age in git**: sops is CNCF Sandbox, active (v3.13.3, 2026-07-23 — [releases](https://github.com/getsops/sops/releases)); age v1.3.2 (2026-08-29); helm-secrets v4.7.7 supports Helm 4 from v4.7.0, split into three plugins under Helm 4's plugin system ([issue #639](https://github.com/jkroepke/helm-secrets/issues/639)). Moving parts: sops + age keypair + plugin in CI + one GH secret (the age key). DR: best of the four — every clone carries all secrets; only the age private key needs out-of-band backup (and it is the single point of failure). Ciphertext in a public repo is world-readable forever, so key hygiene matters.
- **sealed-secrets**: active (v0.40.0, 2026-09-10, now at [bitnami/sealed-secrets](https://github.com/bitnami/sealed-secrets)); exempted from the 2025 Broadcom/Bitnami image freeze ([issue](https://github.com/bitnami-labs/sealed-secrets/issues/1763)). But sealing keys live only on the cluster and rotate every ~30 days (rotation cadence UNVERIFIED against a doc URL) — lose the box without a key backup and every SealedSecret in git is unrecoverable. On a single node it adds a controller while re-creating the back-up-a-key problem with a worse key. SOPS+age dominates it here.
- **External Secrets Operator**: recovered from its mid-2025 maintainer crisis ([health thread](https://github.com/external-secrets/external-secrets/issues/5084)) — releases resumed Sep 2025, v1.0.0 Nov 2025, v2.10.0 Aug 2026, but only the latest minor is supported ([policy](https://external-secrets.io/latest/introduction/stability-support/)): a monthly upgrade treadmill. Heaviest option: controller + CRDs + an external store (e.g. Infisical free tier) + a bootstrap credential. DR is good if the store is SaaS, but it imports a third-party dependency a solo single-box setup doesn't need.

## Shortlist assessment

**Recommended**: OpenTofu (state on R2 with `use_lockfile` + native passphrase encryption; providers hcloud/cloudflare-v5/b2/github; Vast.ai scripted via its CLI/API outside IaC) + GHCR with all layers <10 GB and buildx registry cache + free standard runners with maximize-build-space (self-hosted Hetzner runner on trusted-branch triggers only if the 30 GB end bites) + SSH-tunnel deploy with a namespace-scoped SA-token kubeconfig + SOPS+age via helm-secrets — every piece is free, primary-documented, and survives loss of the box, the repo, or the GitHub account with one age key backed up.

**Runner-up**: Pulumi C# on a DIY R2 backend with `PULUMI_CONFIG_PASSPHRASE` (same providers bridged, b2 via ad-hoc bridge) + the same GHCR/runner choices + Tailscale-action deploy + GitHub environment secrets — buys language unity with the .NET backend and a slicker deploy path, at the cost of Pulumi's weaker blob-storage locking, an unverified R2 pairing, and a write-only secrets store that makes GitHub a single point of failure.
