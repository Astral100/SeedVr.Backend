# Single-box runtime stack survey

Resolves the runtime-stack question left open by ADR 0008 ("K3s + Helm + CloudNativePG vs plain Docker Compose + pgBackRest" — the decision itself belongs to the hosting ticket). Survey of production-credible ways to run the core services — one .NET containerized app (ASP.NET Core API + background services, ~1–2 GB RAM) plus PostgreSQL — on a single self-managed Hetzner CX33 (4 vCPU / 8 GB). Binding requirements from ADR 0008: WAL-based PITR to R2 plus a second offsite copy, automated OS security patching, paging alerts. Wants beyond that: declarative git-owned config, reusability as a framework for future projects, AI-agent-legible CLI/API surface, zero-downtime rolling deploys, a growth path to a second node. GitHub Actions is the CI; Terraform (hcloud) provisions the box. Self-hosted PaaS panels were examined and ruled out separately: Coolify (v4.3.21, near-daily releases, https://github.com/coollabsio/coolify/releases) and Dokploy (v0.30.6, still 0.x, https://github.com/Dokploy/dokploy/releases) both hold state in their own UI/database and back Postgres up with dumps, not WAL — they appear below only in the summary table. All facts verified against primary sources 2026-09-15.

## 1. Cross-cutting: the WAL/PITR toolchain

Whatever the orchestrator, the PITR requirement lands on one of three tools:

1. **pgBackRest** — v2.59.1 (2026-08-17, PostgreSQL 19beta3 support) (https://github.com/pgbackrest/pgbackrest/releases); MIT license, copyright The PostgreSQL Global Development Group and David Steele (https://github.com/pgbackrest/pgbackrest/blob/main/LICENSE); sponsored by AWS, Supabase, pgEdge et al. — not a Crunchy Data product (https://pgbackrest.org/). **Multi-repository is first-class and is the direct answer to "R2 + second offsite copy"**: "The archive-push command will always push WAL to the archive in all configured repositories", with `archive-async=y` preventing one unreachable repo from stalling the others (https://pgbackrest.org/user-guide.html, "Multiple Repositories" / "Asynchronous Archiving"); the `--repo` option ranges [1, 256] (https://pgbackrest.org/command.html). Full/differential/incremental (file- and block-level) backups, parallel and async WAL archiving, client-side AES-256-CBC repo encryption, retention by count or time; repo types include s3 with endpoint override and `repo-s3-uri-style` for S3-compatibles (https://pgbackrest.org/configuration.html, user guide "S3-Compatible Object Store Support"). Containers: no official image exists and the docs take no stance on Docker — `archive_command` runs inside the PG container's environment, so the practical patterns are a custom image extending `postgres` with the pgbackrest package, or host-installed pgBackRest via its SSH/TLS repository-host mode (https://pgbackrest.org/user-guide.html).
2. **WAL-G** — v3.0.9 (2026-08-20), actively maintained (https://github.com/wal-g/wal-g/releases); Apache-2.0 with GPL-3 lzo component (README); development supported by Yandex Cloud (https://github.com/wal-g/wal-g). S3-compatible via `AWS_ENDPOINT` (https://github.com/wal-g/wal-g/blob/master/docs/STORAGES.md); delta backups. **Disqualifier for this requirement: its multiple-storages feature is failover-only, not copy-to-both** — "The primary storage is always used if alive" — and is explicitly experimental (https://github.com/wal-g/wal-g/blob/master/docs/FailoverStorages.md). A second copy would need external bucket sync.
3. **Barman** — 3.20.0 (2026-08-27), GPL-3.0, EnterpriseDB (https://github.com/EnterpriseDB/barman); `barman-cloud-*` supports "AWS S3 (and S3 compatible object stores)" via `--endpoint-url` (https://docs.pgbarman.org/release/3.14.1/user_guide/barman_cloud.html); no multi-repo fan-out. Matters here mostly as the engine inside CloudNativePG's backup plugin (§2).

**Conclusion**: pgBackRest is the only tool that natively satisfies R2-plus-offsite; under every non-Kubernetes option below, "DIY PITR" means "pgBackRest". Note that no primary source (Cloudflare's R2 examples at https://developers.cloudflare.com/r2/examples/ or any tool's docs) names the other party — R2 compatibility rests on generic S3-endpoint support and needs a live probe (see caveats).

## 2. K3s + Helm + CloudNativePG (shortlist A)

1. **PITR machinery**: CloudNativePG v1.30.0 (2026-06-29) (https://github.com/cloudnative-pg/cloudnative-pg/releases), Apache-2.0, CNCF Sandbox since 2025-01-21 (https://www.cncf.io/projects/cloudnativepg/). Packaged WAL archiving + PITR to S3-compatible object stores. **Transition in flight**: in-tree `barmanObjectStore` is "deprecated starting with v1.26" in favor of the Barman Cloud Plugin (CNPG-I), still default for backward compatibility, with native capabilities "being progressively phased out of the core operator" (https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/backup.md, .../wal_archiving.md). The plugin is at v0.15.0 (2026-09-03), Apache-2.0, requires CNPG ≥1.26 (https://github.com/cloudnative-pg/plugin-barman-cloud/releases, https://cloudnative-pg.io/plugin-barman-cloud/docs/intro/); model is an `ObjectStore` CRD + `isWALArchiver: true` (https://cloudnative-pg.io/plugin-barman-cloud/docs/usage/). New deployments should start on the plugin. **Second offsite copy: not provided** — "Only one plugin at a time can be responsible for WAL archiving" (wal_archiving.md); multiple ObjectStores serve different roles (archive vs recovery source), not dual archiving. The offsite copy must be object-storage-level replication (e.g. scheduled rclone R2→elsewhere) — so even option A carries one DIY backup component. **Distro support caveat**: CNPG officially supports/tests only vanilla Kubernetes ("the CloudNativePG community does not officially support or test any Kubernetes distributions beyond the standard/vanilla one", OpenShift excepted via EDB) (https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/supported_releases.md); K3s is CNCF-conformant Kubernetes (v1.33 conformance submission: https://github.com/cncf/k8s-conformance/tree/master/v1.33) so it runs, but "unsupported/untested" is the official posture. 1.30.x supports K8s 1.34–1.36, with 1.37 "tested but unsupported" (supported_releases.md) — pin the K3s channel accordingly.
2. **Declarative**: fully — manifests/Helm charts in git; Flux (CNCF Graduated 2022-11-30, https://www.cncf.io/projects/flux/) is realistic on this box: its scaling docs say tuning is only needed "when Flux is managing hundreds of applications deployed multiple times per day" (https://fluxcd.io/flux/installation/configuration/vertical-scaling/). Helm is now major version 4 (v4.3.0, 2026-09-09, https://github.com/helm/helm/releases; v4.0.0 at KubeCon 2025-11-12); Helm 3 security fixes end 2026-11-11 (https://helm.sh/blog/helm-4-released/) — start on Helm 4.
3. **Reusability**: highest of the field — charts/kustomizations are the industry-standard template unit, and everything learned transfers to any Kubernetes anywhere.
4. **Agent legibility**: `kubectl` + typed API + `helm` is the best-documented control surface in existence; enormous training corpus; everything is queryable/diffable.
5. **Idle overhead**: official server minimum 2 cores / 2 GB RAM; a 4 CPU/8 GB server is K3s's sizing row for 351–900 agents (https://docs.k3s.io/installation/requirements). Measured (secondary, Portainer 2023): ~750 MB total system at idle (https://www.portainer.io/blog/k0s-vs-k3s). CNPG operator requests 100Mi / limit 200Mi (release manifest https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/releases/cnpg-1.30.0.yaml). Realistic stack (K3s + CNPG + Flux + PG + app) fits 8 GB with room, but budget ~1.5–2 GB for the platform itself.
6. **Maturity/governance**: K3s v1.37.0+k3s1 (2026-09-14), tracking upstream K8s patch releases (https://github.com/k3s-io/k3s/releases); Apache-2.0; CNCF Sandbox since 2020 with an **incubation application open at the TOC** (https://www.cncf.io/projects/k3s/, https://github.com/cncf/toc/issues/1957); maintained by SUSE/Rancher (https://www.rancher.com/products/k3s).
7. **Rolling deploys**: native Deployments give the app zero-downtime out of the box. For Postgres, CNPG rolling updates upgrade replicas first and the primary last (`primaryUpdateStrategy`, `primaryUpdateMethod: restart|switchover`), but the docs are honest: "the update process inevitably generates a downtime for your applications" — and with a single PG instance every update is a restart blip (https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/docs/src/rolling_update.md).
8. **Growth**: single-node is the documented default (`curl … | sh -` "creates a fully functional single-node cluster", https://docs.k3s.io/quick-start); SQLite is the default datastore, embedded etcd or external DB for multi-server (https://docs.k3s.io/datastore); a second node is one `K3S_URL`/`K3S_TOKEN` agent join. Note SQLite → multi-server requires a datastore migration or starting with embedded etcd.

## 3. k0s

The credible lighter-weight alternate to K3s. v1.36.4+k0s.0 (2026-08-31; one K8s minor behind K3s at check time) (https://github.com/k0sproject/k0s/releases); Apache-2.0 code (https://github.com/k0sproject/k0s — LICENSE splits docs under CC-BY-SA); donated by Mirantis to CNCF, Sandbox since 2025-01-19 (https://www.cncf.io/projects/k0s/, https://www.mirantis.com/company/press-center/company-news/k0s-kubernetes-and-k0smotron-join-cncf-sandbox-in-next-stage-of-development/). Lowest official floor: controller+worker minimum 1 GB / 1 vCPU (https://docs.k0sproject.io/stable/system-requirements/); measured ~658 MB idle, lightest in Portainer's comparison (secondary, https://www.portainer.io/blog/k0s-vs-k3s). Single-node is explicit — but `k0s install controller --single` "disables features needed for multi-node clusters, so the cluster cannot be extended"; the growth-compatible form is `--enable-worker --no-taints` (https://docs.k0sproject.io/stable/install/). etcd default datastore; HA needs 3 controllers + external LB (https://docs.k0sproject.io/stable/high-availability/). CNCF-conformant (https://github.com/cncf/k8s-conformance/tree/master/v1.33). Same CNPG/Helm/Flux story as K3s. Trade-off vs K3s: marginally lighter and CNCF-donated, but smaller ecosystem/mindshare, Mirantis provenance (Mirantis was acquired by IREN 2026-08-04, §8), and it trails upstream minors.

## 4. MicroK8s

v1.36 on GitHub (2026-05-25) but the snap default channel and getting-started guide were on 1.35/stable at check time (https://github.com/canonical/microk8s/releases, https://snapcraft.io/microk8s, https://canonical.com/microk8s/docs/getting-started). Apache-2.0; Canonical product, **not a CNCF project**; CNCF-conformant (https://github.com/cncf/k8s-conformance/tree/master/v1.33). "Runs in as little as 540MB of memory", 4 GB recommended (https://canonical.com/microk8s/docs/getting-started); ~685 MB measured (secondary, Portainer). Single-node default on dqlite; `add-node`/`join` with automatic HA at 3+ nodes (https://canonical.com/microk8s/docs/high-availability). The disqualifying friction for this stack: it is delivered only as a snap, coupling the box to snapd, and its single-vendor non-CNCF governance plus addon-oriented UX make it the least template-portable of the three small distros. Same CNPG story otherwise.

## 5. RKE2

v1.37.0+rke2r1 (2026-09-14) (https://github.com/rancher/rke2/releases); Apache-2.0; SUSE/Rancher, security/FIPS-hardened positioning; conformance submitted as "rke-government" (https://github.com/cncf/k8s-conformance/tree/master/v1.33/rke-government). **Out on requirements alone**: "RAM: 4GB Minimum (we recommend at least 8GB)", 2 CPU min / 4 recommended (https://docs.rke2.io/install/requirements) — the recommendation is the entire CX33 before the workload runs. Embedded etcd is the only embedded datastore (https://docs.rke2.io/datastore/embedded), heavier than K3s's SQLite. Right tool for compliance-driven clusters, wrong tool for an 8 GB single box.

## 6. Talos Linux

v1.14.1 (2026-09-15) (https://github.com/siderolabs/talos/releases); **MPL-2.0** — the only non-Apache K8s option here; Sidero Labs, not CNCF; conformant (https://github.com/cncf/k8s-conformance/tree/master/v1.33). An immutable, API-only OS (no SSH, no shell) that *is* the node: machine config + `talosctl` replace the OS layer entirely. Control plane minimum 2 GiB / 2 cores, 4 GiB recommended; amd64 needs x86-64-v2 (https://docs.siderolabs.com/talos/v1.14/getting-started/system-requirements). An official Hetzner Cloud guide exists (custom snapshot upload via rescue-mode dd/Packer/hcloud-upload-image, then `hcloud server create`) but its flow assumes 3 control planes + a load balancer (https://docs.siderolabs.com/talos/v1.14/platform-specific-installations/cloud-platforms/hetzner). Architecturally the purest declarative option (the OS itself is git-owned config, which would also subsume the OS-patching requirement), but it conflicts with the ADR's ergonomics: no Hetzner native image, single-node not the design center, and agent-assisted ops lose the SSH escape hatch. A compelling second-generation template once there are 3+ nodes; overkill for one CX33.

## 7. Docker Compose + systemd + pgBackRest (shortlist B)

1. **PITR machinery**: DIY pgBackRest (§1) — which is also the only path in the whole survey to native R2-plus-offsite WAL fan-out. Custom `postgres`-derived image with pgbackrest installed (archive_command must run inside the PG container), config in git, cron/systemd-timer for scheduled backups and retention.
2. **Declarative**: compose.yaml is the source of truth; runtime state lives only in labeled Docker objects (https://docs.docker.com/compose/intro/compose-application-model/). Weaker than Kubernetes in that nothing reconciles drift — `docker compose up` converges only when run — but there is no hidden UI/DB state. systemd units, unattended-upgrades config, and pgbackrest.conf complete the git-owned picture.
3. **Reusability**: moderate — a compose file + Caddy/Traefik + pgBackRest recipe copies cleanly between projects, but it is a convention you maintain, not an ecosystem artifact like a chart.
4. **Agent legibility**: excellent — `docker`/`docker compose` are as deeply represented in training data as kubectl, and the whole state surface is a handful of inspectable objects.
5. **Idle overhead**: lowest of any engine-based option; no official figure exists for dockerd+containerd (anecdotally ~100–200 MB — unverified). Essentially the whole 8 GB goes to the workload.
6. **Maturity/license**: Compose is now **v5** — v5.5.1 (2026-09-03); v5.0.0 (2025-12-02) skipped v3/v4 to avoid confusion with the old file-format versions and delegated builds to Bake (https://github.com/docker/compose/releases/tag/v5.0.0). Apache-2.0 (https://github.com/docker/compose/blob/main/LICENSE). Docker Engine v29.8.1 (2026-09-15), Apache-2.0 (https://github.com/moby/moby/releases, https://github.com/moby/moby/blob/master/LICENSE); the paid-subscription rule attaches to Docker Desktop, not server Engine (https://docs.docker.com/engine/).
7. **Rolling deploys**: **none native as of v5.5.1** — `docker compose up` stops and recreates changed services; `--wait`/`--wait-timeout` gate on health but do not roll (https://docs.docker.com/reference/cli/docker/compose/up/). The Compose file's `update_config`/`rollback_config` keys only take effect under Swarm's `docker stack deploy` (https://docs.docker.com/reference/compose-file/deploy/). Zero-downtime is DIY: two replicas behind Traefik/Caddy with drain, or the third-party `docker rollout` plugin (https://github.com/Wowu/docker-rollout). ADR 0008 already notes deploy-blip tolerance is moot for the current pipeline design, so this is a want, not a requirement.
8. **Growth**: none — multi-node is Swarm's job (https://docs.docker.com/engine/swarm/). A second node means re-platforming (to Swarm, Kamal, or K8s) or manual placement.

## 8. Docker Swarm mode

The under-discussed middle: everything in §7 plus native orchestration, from the same engine already installed. Single-node swarm is explicitly supported (https://docs.docker.com/engine/swarm/swarm-tutorial/); `docker stack deploy` consumes Compose files; **rolling updates are built in** — `--update-order start-first`, `--update-parallelism`, `--update-failure-action rollback` (https://docs.docker.com/reference/cli/docker/service/update/); secrets live encrypted in the Raft log, mounted as tmpfs (https://docs.docker.com/engine/swarm/secrets/); a second node is one `docker swarm join`. Declarative caveat: stack files are git-owned, but secrets contents, service history, and membership live only in cluster Raft state. The real question is momentum: swarmkit is demonstrably alive (last commit 2026-09-15, v2.1.2 released 2026-04-23, https://github.com/moby/swarmkit) but feature-frozen in practice, and its corporate sponsor chain got murkier — Mirantis pledged Swarm support "through 2030" (https://www.mirantis.com/blog/mirantis-guarantees-long-term-support-for-swarm/) but **IREN completed its acquisition of Mirantis 2026-08-04** with an AI-cloud rationale (https://iren.gcs-web.com/news-releases/news-release-details/iren-completes-acquisition-mirantis) and no post-acquisition reaffirmation of that pledge was found. Postgres story identical to §7 (pgBackRest DIY; note Swarm's rolling updates don't help a single-instance stateful PG anyway). Verdict: a cheap upgrade path *from* option B if rolling deploys become wanted, not a foundation to standardize a multi-project framework on in 2026.

## 9. Podman + Quadlet (systemd units)

Podman v6.1.1 (2026-09-02; 5.8.x still maintained), Apache-2.0, repo now under podman-container-tools; CNCF Sandbox since 2025-01-21 under LF Projects (https://github.com/podman-container-tools/podman, https://www.cncf.io/projects/podman-container-tools/, https://podman.io/). Quadlet is the most literal "git-owned declarative + systemd" design here: `.container`/`.pod`/`.kube`/`.network`/`.volume` unit files in `/etc/containers/systemd/`, generated into services on daemon-reload, managed "with systemctl like any other systemd service"; `.kube` units even run Kubernetes YAML locally; rootless is fully supported (https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html). `podman auto-update` pulls new images on a label, restarts the unit, and **rolls back by default on failed restart** (https://docs.podman.io/en/latest/markdown/podman-auto-update.1.html) — a nice unattended-patching fit. Daemonless, so no idle engine process. The disqualifiers against the two shortlisted options: **no zero-downtime mechanism at all** (updates are systemd unit restarts), **no multi-node path**, and badly lagging distro packages — Ubuntu 24.04 LTS ships 4.9.3 and Debian trixie 5.4.2 against upstream 6.1.1 (https://packages.ubuntu.com/search?keywords=podman, https://packages.debian.org/search?keywords=podman) — so a current Podman means third-party repos or source builds on the target OS. Postgres: pgBackRest DIY, same as §7. Strong for a hardened single-service host; weaker than Compose on ecosystem tooling and than K3s on everything orchestration.

## 10. Kamal 2

v2.12.0 (2026-06-18; steady quarterly cadence) (https://github.com/basecamp/kamal/releases, https://kamal-deploy.org/); MIT (https://github.com/basecamp/kamal/blob/main/MIT-LICENSE); built and production-used by 37signals for HEY, Basecamp, ONCE (https://kamal-deploy.org/). Deploys Docker images to bare servers over SSH; **kamal-proxy** (which replaced Traefik in Kamal 2) health-checks the new container then switches traffic — genuine zero-downtime for the app, plus auto-SSL (https://kamal-deploy.org/docs/configuration/proxy/, https://github.com/basecamp/kamal-proxy). Config is `config/deploy.yml` in git; `.kamal/secrets` holds fetch commands with 1Password/Bitwarden/AWS/GCP/Doppler adapters, not values (https://kamal-deploy.org/docs/commands/secrets/). Multi-server is one line per host in a role (https://kamal-deploy.org/docs/configuration/roles/), and app + proxy + accessories co-locate on one box fine (https://kamal-deploy.org/docs/configuration/accessories/). The Postgres catch, verbatim from the docs: "Accessories are managed separately from the main service — they are not updated when you deploy, and **they do not have zero-downtime deployments**" (same accessories page) — and Kamal has no scheduler, no self-healing beyond Docker restart policies, and no backup feature of any kind, so PITR is the same pgBackRest DIY as option B. Honest framing: Kamal 2 is option B with the zero-downtime deploy problem solved and a cleaner CLI story (`kamal deploy` from GitHub Actions), at the cost of a Ruby toolchain in CI and 37signals-shaped opinions (built around one primary web app per config; the API + background services fit as roles).

## 11. HashiCorp Nomad

**License: BUSL-1.1, non-OSS** — and the repo LICENSE's licensor now reads "International Business Machines Corporation" (https://github.com/hashicorp/nomad/blob/main/LICENSE); production use is allowed unless competitive with IBM/HashiCorp offerings. IBM completed the HashiCorp acquisition 2025-02-27 (https://ir.hashicorp.com/news-releases/news-release-details/ibm-completes-acquisition-hashicorp-creates-comprehensive-end). Actively developed: now "Nomad 2.0" — v2.0.6 released 2026-09-09, with the major bump being IBM lifecycle alignment (V.M.F versioning, support to 2028) rather than breaking changes (https://releases.hashicorp.com/nomad/, https://developer.hashicorp.com/nomad/docs/release-notes/v2-0-x); no primary-source deprioritization statement exists — only community speculation. Rolling updates and canaries are first-class in the job spec (`update` block: `max_parallel`, `canary`, `auto_revert`) (https://developer.hashicorp.com/nomad/docs/job-specification/update), and HCL job specs are cleanly git-owned. Disqualifiers for this box: running one agent as both server and client is supported but recommended against for production (https://developer.hashicorp.com/nomad/docs/deploy/nomad-agent), the production requirements page recommends 4–8+ cores / **16–32 GB+** servers in a 3–5 quorum with no small-deployment guidance (https://developer.hashicorp.com/nomad/docs/deploy/production/requirements), and **no CloudNativePG-equivalent exists for Nomad** — Postgres is a plain task + pgBackRest DIY. BSL license + IBM governance + no PG operator + anti-single-node posture: dominated by both shortlisted options for this workload.

## 12. Uncloud and other also-rans

- **Uncloud** (https://github.com/psviderski/uncloud): Apache-2.0, ~5.5k stars, v0.20.0 (2026-06-26); Docker-based multi-machine tool with WireGuard mesh, Caddy ingress, Compose-format config, zero-downtime rolling deploys, and no control plane. On paper the closest match to the whole wish-list outside Kubernetes — but the README itself says "under active development and pre-1.0" with possible breaking changes. Watch, don't adopt.
- **Portainer** (2.45.0 LTS, https://github.com/portainer/portainer/releases): management UI over Docker/Swarm/K8s, state in its own database behind a UI — the opposite of git-owned; not an orchestrator.
- **CapRover** (v1.15.4, https://github.com/caprover/caprover/releases): alive, but UI/CLI-driven PaaS with server-held app state; same category Coolify/Dokploy were ruled out of.
- **Incus/LXD**: system-container manager, not an OCI application platform — not relevant.

## Shortlist assessment

Both shortlisted options survive contact with primary sources; the survey adds one genuine challenger and demotes one assumed component.

### A. K3s + Helm 4 + Flux + CloudNativePG (Barman Cloud Plugin)
Still the strongest "reusable framework" play: fully declarative and reconciled, the industry-standard template unit (charts), the best agent-facing control surface, native rolling deploys, and a real second-node path — for ~1.5–2 GB of the box. Three corrections to the mental model from this pass: (1) CNPG **cannot dual-archive**, so the second offsite copy is bucket-level sync (rclone) under A exactly as it would be a pgBackRest repo under B — A's packaged-PITR advantage is real but narrower than "no DIY at all"; (2) CNPG officially tests only vanilla K8s — K3s works as conformant Kubernetes but rides unsupported; (3) the in-tree backup path is deprecated mid-transition to the Barman Cloud Plugin — adopt the plugin from day one and accept that the packaged machinery is itself in motion. If A is chosen, k0s is the only alternate worth a second look (lighter floor, CNCF-donated) but K3s's ecosystem, currency (1.37 vs 1.36), and open incubation application make it the default.

### B. Docker Compose v5 + systemd + pgBackRest
Verified leaner and more honest than its reputation: everything is Apache-2.0, the state model is transparent, and **pgBackRest is the single best PITR tool in the entire survey** — the only one that natively fans WAL out to R2 plus a second repo with per-repo retention and encryption, which is precisely ADR 0008's binding requirement. B's confirmed weaknesses: no rolling deploys (recreate blip; third-party plugin or proxy DIY to fix), no drift reconciliation, and no growth path without re-platforming. Swarm is the natural pressure-relief valve for both weaknesses but is not a 2026 foundation (frozen momentum, Mirantis→IREN uncertainty).

### The challenger: Kamal 2 + pgBackRest
MIT, production-proven at 37signals, config-in-git, secrets adapters, GitHub-Actions-friendly, multi-server-ready — and it deletes B's biggest gap by shipping zero-downtime app deploys via kamal-proxy. Its Postgres story is exactly B's (accessory with restart downtime + pgBackRest DIY), so it competes purely as "B with better deploys and a smaller bespoke-script surface". If the decision ticket leans B, Kamal 2 deserves a head-to-head before writing custom deploy scripts.

**Eliminated with cause**: RKE2 (4 GB min/8 GB recommended eats the box), Talos (immutable-OS elegance, wrong scale — 3-CP Hetzner flow, no SSH escape hatch for agent ops), MicroK8s (snapd coupling, non-CNCF single-vendor), Nomad (BUSL non-OSS, IBM-owned, anti-single-node production posture, no PG operator), Podman/Quadlet (no zero-downtime, no growth path, stale distro packages — though `podman auto-update`'s rollback is worth stealing as an idea), Swarm (viable but momentum-frozen), Uncloud (pre-1.0), WAL-G (failover-only multi-storage fails the offsite requirement pgBackRest meets natively).

## Verification caveats

Claims not fully confirmable from primary sources:

- **Cloudflare R2 compatibility with pgBackRest / WAL-G / barman-cloud / CNPG's Barman plugin**: no primary source on either side names the other. All support custom S3 endpoints and community reports say R2 works (pgBackRest historically needing URI-style/TLS-verify tweaks), but **a live probe against R2 belongs in the decision ticket before locking the stack** (check POC PLAN.md for any prior probes first).

- **Compose "no rolling updates"** is an absence claim from official CLI/spec docs and v5.0.0–v5.5.1 release notes, not an explicit statement. Likewise **Kamal "no backup/no self-healing"** — verified by absence across kamal-deploy.org docs; the accessory-downtime quote is verbatim.
