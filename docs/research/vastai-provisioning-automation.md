# Vast.ai provisioning automation: official story vs. practice

Date: 2026-09-17

**TL;DR.** Vast.ai has no IaC product and no official GitHub Action; its official automation story is "drive the CLI/SDK/REST API from your own scripts", now supplemented by two newer official layers: a Python-native "Deployments" workflow (open beta, defines image + autoscaling entirely in code with content-hash change detection) and agent skills/plugins that wrap the CLI. Templates *can* be updated in place (`vastai update template HASH_ID --image_tag ...`), but the template's `hash_id` changes on every edit (content-derived) while its numeric `id` stays stable; serverless workergroups reference templates by `template_hash` or `template_id`, and worker replacement is a documented rolling update (`vastai update workers`) that never interrupts in-flight requests. Scoped API keys exist and the docs explicitly recommend minimal-permission keys for CI/CD. Practitioners on GitHub overwhelmingly use small bash/CLI steps in workflows — almost all for ephemeral *instances* (batch jobs/benchmarks), with a pre-made template referenced by hash from a repo secret; public examples of serverless template/endpoint updates from CI are essentially nonexistent, so our CI shape will be self-assembled from documented primitives, not copied from an established pattern.

## 1. What Vast.ai's own docs recommend

- **No canonical CI/GitOps pattern.** The serverless setup guide is UI-first (Serverless Dashboard, "changes take effect immediately" via the edit pencil) and offers no IaC/environments guidance (https://docs.vast.ai/guides/serverless/setting-up-endpoints). There is no official GitHub Action (searches of the marketplace and the vast-ai org find none; integrations offered are CLI, SDK, REST API, and editor/agent plugins — https://github.com/vast-ai). The closest thing to an official automation doctrine is the docs index itself being agent-consumable (`https://docs.vast.ai/llms.txt`) plus a guide on driving Vast from coding agents via a `vastai` skill and Claude Code/Codex/Cursor plugins, which explicitly lists serverless endpoint and template management as automatable tasks (https://docs.vast.ai/guides/get-started/agents).
- **Full CRUD exists in CLI and REST for every object we need:**
  - Templates: `vastai create template --name --image --image_tag --env --onstart-cmd --disk_space ...` (https://docs.vast.ai/cli/reference/create-template); **`vastai update template HASH_ID`** exists and updates in place, with `--image`, `--image_tag`, `--env`, etc. (https://docs.vast.ai/cli/reference/update-template). REST: `POST/PUT/DELETE https://console.vast.ai/api/v0/template/`; PUT takes `hash_id` and only changed fields (https://docs.vast.ai/api-reference/creating-and-using-templates-with-api).
  - **Hash semantics (critical):** a template has a stable numeric `id` and a content-derived `hash_id`; "the template's `hash_id` will change after editing (since it's content-based), but the numeric `id` stays the same" — the PUT response returns the new `hash_id` (https://docs.vast.ai/api-reference/templates/edit-template). So in-place update to a new image tag is supported, but anything referencing the old hash points at pre-edit content.
  - Endpoints: `vastai create endpoint` / `update endpoint` / `delete endpoint` (CLI) and `POST https://console.vast.ai/api/v0/endptjobs/` with `endpoint_name`, `min_load`, `target_util`, `cold_mult`, `cold_workers`, `max_workers` (https://docs.vast.ai/api-reference/serverless/create-endpoint).
  - Workergroups (the object binding endpoint↔template): `vastai create/update/delete workergroup`; `PUT /api/v0/workergroups/{id}` accepts `template_hash` **or** `template_id`, plus `search_params`, `gpu_ram`, `launch_args`, endpoint linkage (https://docs.vast.ai/api-reference/serverless/update-workergroup, https://docs.vast.ai/cli/reference/update-workergroup).
- **CI auth: scoped API keys exist and are the documented CI story.** `vastai create api-key --permission_file <json>` creates keys restricted to permission categories; the docs explicitly call out "CI/CD that creates and destroys instances → Instance management only", warn that default keys have full account access including billing and key management, recommend GitHub Actions secrets / never committing keys, and describe manual rotation via Reset (no automatic expiry; 90-day rotation suggested) (https://docs.vast.ai/guides/reference/api-keys, https://docs.vast.ai/api-reference/permissions, https://docs.vast.ai/cli/reference/create-api-key).

## 2. The Python SDK

- `pip install vastai` ships CLI + SDK in one package; the SDK (`vastai_sdk.VastAI()`) mirrors the CLI 1:1 — every command above exists as a method (`create_template`, `update_template`, `create_endpoint`, `update_endpoint`, `create_workergroup`, `update_workergroup`, `update_workers`, `create_api_key`, ...) with the same arguments (https://github.com/vast-ai/vast-sdk, https://docs.vast.ai/sdk/python/reference/update-template). A Python script driving this is a fully intended path, but it is a thin imperative wrapper — no desired-state/diffing.
- **"Deployments" (open beta since ~April 2026) is the real code-first offering:** a `Deployment` object defined entirely in Python — `image(from_image)` (custom Docker image + tag supported), `pip_install`, `configure_autoscaling(cold_workers, max_workers, target_util, target_queue_time, inactivity_timeout, ...)`, then `ensure_ready()`, which packages code+config, "computes a content hash to determine if anything has changed", registers the deployment, and "triggers the appropriate update tier if workers are already running"; changing the image `tag` "triggers a full redeploy with a new endpoint"; optional `version_label`, and `vastai show deployment-versions` exposes history (https://docs.vast.ai/guides/serverless/deployments/configuration, https://vast.ai/article/april-2026-product-update). This is idempotent-by-content-hash — closest thing Vast has to declarative IaC — but it is beta and built around the @remote Python-function model layered on pyworker.
- The `vast-ai/pyworker` repo (worker implementations for serverless templates) covers only the in-container side (`PYWORKER_REPO`/`PYWORKER_REF` env vars clone worker code at startup); it contains **no** template/endpoint lifecycle scripts or CI examples (https://github.com/vast-ai/pyworker).

## 3. What practitioners do

- **The established pattern is "small bash step calling the vastai CLI from GitHub Actions" — but almost entirely for ephemeral instances, not serverless.** GitHub code search for `vastai` in `.github/workflows` finds ~a dozen real repos (e.g. yetanotherco/lambda_vm `benchmark-gpu.yml`, JhnsonO/ffa-automations render pipelines, LiibanMo/geomflow): the canonical shape is `vastai set api-key` from a secret → `vastai search offers --raw` + `jq` to pick an offer → `vastai create instance $OFFER_ID --template_hash "$VAST_TEMPLATE_HASH"` (template pre-made once, its hash stored as a repo secret) → poll `vastai show instance --raw` → SSH in, run, `vastai destroy instance` (https://github.com/yetanotherco/lambda_vm/blob/main/.github/workflows/benchmark-gpu.yml).
- **Public examples of serverless endpoint/template management from CI: effectively none.** GitHub-wide code searches for `"vastai update template"` and `vastai update workergroup` in workflows return only Vast's own docs/CLI repos, doc mirrors, and agent-skill repos (vast-ai/vast-claude-plugin, LiorZ/vastai-claude-skill) — no third-party CI pipelines. No blog posts or Reddit/forum threads on Vast serverless CI/CD or "Vast.ai as code" surfaced in searches. Conclusion: the serverless product is young enough that there is no community-established pattern to copy; the instance-workflow habits (secret-held template hash, CLI + jq, `--raw` JSON) are what transfers.
- **Contrast — RunPod:** the equivalent problem there is solved and documented: RunPod offers native GitHub integration (RunPod pulls the repo, builds the image, deploys to the endpoint — https://docs.runpod.io/serverless/github-integration), and the common DIY pattern is a CI step calling the SDK's `update_endpoint_image` / GraphQL "save template with new tag" after pushing the image (e.g. https://lucaschmid.net/blog/runpod-deploy/), plus a marketplace Action that spins up temporary endpoints for tests. Vast has no counterpart to the build-from-GitHub service; on Vast you push the image to a registry yourself and repoint the template.

## 4. Gotchas for our design

- **Running workers are not changed by a template edit alone.** The documented rollout is: modify the template, point the workergroup at it, and a **rolling update** proceeds — "Inactive workers become active and update, Active workers finish existing tasks first, New requests route to updated workers"; "active workers are never interrupted mid-request" (https://docs.vast.ai/guides/serverless/zero-downtime-worker-update). `vastai update workers <workergroup_id>` explicitly triggers this rolling cycle ("the autoscaler will cycle through workers, updating them while maintaining capacity") and supports `--cancel` (https://docs.vast.ai/cli/reference/update-workers).
- **Hash churn vs stable id.** Workergroups accept `template_id` (stable across edits) or `template_hash` (changes every edit). If you reference by hash, every image-tag bump requires a follow-up `update workergroup --template_hash <new>`; referencing by `template_id` avoids repointing. UNVERIFIED: whether a workergroup bound by `template_id` automatically rolls workers after a template edit, or still needs an explicit `update workers` kick — the docs never state it; assume the explicit kick is required and always call it.
- **Template "versioning" is implicit only:** old `hash_id`s encode prior content and `show deployment-versions` exists only for the beta Deployments product; classic templates have no listed history/rollback. Rollback = re-issue `update template` with the previous tag (or keep per-release templates). UNVERIFIED: no documented limit on template count was found anywhere in docs.
- The zero-downtime guide advises verifying a new template on a **separate staging endpoint** first and scheduling updates in low-traffic windows (https://docs.vast.ai/guides/serverless/zero-downtime-worker-update).
- Rate limits apply to the API/CLI and 429s are documented — retry/backoff belongs in the CI step (https://docs.vast.ai/api-reference/rate-limits-and-errors).
- Avoid mutable `:latest`-style tags as a dodge: nothing in the serverless docs re-pulls images on idle workers UNVERIFIED; the documented refresh path is the rolling worker update, so pin immutable tags and roll explicitly — that also keeps what's deployed inspectable.

## Assessment

**Recommended shape:** a small idempotent Python script (checked into this repo) driving the `vastai` SDK/CLI, run by a GitHub Actions job after the worker-image push: it ensures endpoint + workergroup exist with our declared scaling config (create-or-update), calls `update_template HASH --image_tag <release tag>`, repoints the workergroup at the returned new `template_hash` (sidestepping the id-vs-hash propagation ambiguity), then calls `update workers` to trigger the documented zero-downtime rolling replacement, and polls workergroup workers until the new tag is serving. Auth via a scoped API key (minimum permission categories, stored as a GH Actions secret, 90-day manual rotation). Desired state (scaling params, GPU search_params, env) lives in a versioned config file the script applies — that is the whole "IaC" layer, matching both Vast's primitives and the community's CLI-in-CI idiom.

**Runner-up:** adopt Vast's beta **Deployments** workflow (`Deployment(...).image(...).configure_autoscaling(...).ensure_ready()`) as the declarative layer — content-hash idempotence and version history for free — accepting beta churn and its @remote/pyworker-shaped model; revisit once it exits beta. Not recommended now: any Terraform/OpenTofu route (no credible provider, per docs/research/cicd-iac-landscape.md) or mutable-tag templates.
