# Vast.ai Serverless — capabilities and fit for ComfyUI + SeedVR2

Research for issue #2. All claims cite primary sources: docs.vast.ai, the `vast-ai/pyworker` and `vast-ai/vast-sdk` GitHub repos (source code read directly), and official Vast.ai pages. Researched 2026-08-27.

**Verdict: fit-with-caveats.** Vast.ai serverless has a first-party ComfyUI path (ComfyUI (Serverless) template + `comfyui-json` PyWorker + the ai-dock ComfyUI API wrapper) whose request contract — `input.request_id`, `input.workflow_json`, `input.s3`, `input.webhook`, S3 presigned-URL delivery — is exactly the contract our POC wrapper already documents. The caveats: no .NET SDK (we must reimplement a small, verified 2-step HTTP protocol), multi-GB model cold starts must be engineered around, one request per ComfyUI worker at a time, and the platform is young (launched late 2025). Details and integration sketch in §6.

---

## 1. How Vast.ai serverless works

### Components

- **Endpoint (group)** — top-level construct; holds scaling config (`min_workers` default 5, `max_workers` default 16, `target_util` default 0.9, `cold_mult` default 3, max/target queue time, optional inactivity timeout for scale-to-zero). Source: https://docs.vast.ai/guides/serverless/architecture and https://docs.vast.ai/guides/serverless/setting-up-endpoints
- **Workergroup** — defines *what* runs on workers: a template (`template_hash` or `template_id`), `gpu_ram` (default 24 GB), `launch_args`, and `search_params` — a filter query over the GPU marketplace (same operators/fields as offer search, e.g. `{"verified": {"eq": true}, "rentable": {"eq": true}}`). Typically one workergroup per endpoint; several allowed. Source: https://docs.vast.ai/guides/serverless/workergroup-parameters
- **Worker** — an individual GPU instance running **PyWorker**, "a Python web server that monitors the inference server's readiness, proxies incoming requests, and coordinates with the autoscaler". Source: https://docs.vast.ai/guides/serverless/architecture
- **Serverless Engine (autoscaler)** — decides "when to recruit new workers, activate inactive workers, release or destroy workers" from reported metrics; each worker runs a startup benchmark whose score informs request distribution and capacity estimates. Sources: https://docs.vast.ai/guides/serverless/architecture , https://docs.vast.ai/guides/serverless/comfy-ui
- **PyWorker** — MIT-licensed proxy framework; example workers live in https://github.com/vast-ai/pyworker (`workers/`: `comfyui-json`, `wan`, `ace`, `vllm`, `sglang`, `llama`, `openai`, `tgi`); the framework itself lives in the `vastai` PyPI package (repo https://github.com/vast-ai/vast-sdk , `vastai/serverless/server/`). Source: https://github.com/vast-ai/pyworker (README)

### Request routing (verified from SDK source, replicable from C#)

The official client is the Python SDK (`pip install vastai`; `client.get_endpoint(name=...)`, `endpoint.request(route, payload, cost=...)`) — https://docs.vast.ai/guides/serverless/quickstart . Under the hood it is plain HTTPS, read from `vastai/serverless/client/{client,endpoint,connection}.py` in https://github.com/vast-ai/vast-sdk :

1. **Route call** — `POST https://run.vast.ai/route/` with header `Authorization: Bearer <API key>` and body
   `{"endpoint": "<endpoint-name>", "api_key": "<key>", "cost": <workload-float>, "request_idx": 0, "replay_timeout": 60.0}`.
   The response either contains `"url"` (a worker address → READY) or not (→ WAITING; the SDK polls `/route/` with jittered exponential backoff, reusing the returned `request_idx` so the queued position is kept). Source: `endpoint.py` `_route()` / `RouteResponse`; base URL constant `VAST_SERVERLESS_URL = "https://run.vast.ai"` in `client.py`.
2. **Worker call** — `POST {worker_url}{route}` (e.g. `/generate/sync`) with the same Bearer header and body
   `{"auth_data": <entire /route/ response body>, "session_id": null, "payload": <your payload>}`.
   The worker's PyWorker validates `auth_data` (it carries the routing signature) and proxies to the local model server; the response returns directly from the worker to the client. On connection failure the SDK re-routes to a new worker and retries. Source: `client.py` `_do_request()`.
3. Default worker-call timeout in the SDK is 600 s (`worker_timeout`), with an outer `timeout` covering routing+retries. Source: `client.py` `_do_request()` signature.

**Authentication** is the Vast API key as `Authorization: Bearer` on both calls (plus the key repeated in the `/route/` body); the endpoint object also carries its own `api_key` field, so endpoint-scoped keys are supported by the data model. Sources: `connection.py` (`headers = {"Authorization": f"Bearer {api_key}"}`), `endpoint.py`.

### Sizing signals

Each request declares a `cost` (workload units — tokens for LLMs, a fixed `100` for ComfyUI). PyWorker's startup benchmark measures the worker's capacity in the same units; the engine compares aggregate declared load vs capacity to scale. Sources: https://docs.vast.ai/guides/serverless/creating-new-pyworkers , https://github.com/vast-ai/pyworker/tree/main/workers/comfyui-json (README: "The cost for each request has a static value of `100`").

## 2. Docker template requirements; where models live; cold starts

- A workergroup points at a normal Vast **template**: Docker image (any public registry image), env vars, ports, on-start script, disk size. Source: https://docs.vast.ai/guides/templates/creating-templates
- For serverless, the image's start script must launch the model server **and** the PyWorker: the template's `start-server` script clones the repo named in the `PYWORKER_REPO` env var (`PYWORKER_REF` picks a branch/tag), installs `requirements.txt`, starts the model server, and runs `python worker.py`. A custom worker is one `worker.py` building a `WorkerConfig` (model server URL/port, log file for readiness detection, `HandlerConfig` per route with a `workload_calculator`, optional `BenchmarkConfig`). Source: https://docs.vast.ai/guides/serverless/creating-new-pyworkers
- **First-party ComfyUI path**: the "ComfyUI (Serverless)" template bundles ComfyUI + the ai-dock ComfyUI API Wrapper + SD1.5 for benchmarking; the matching PyWorker is `workers/comfyui-json`. "This worker requires both ComfyUI and ComfyUI API Wrapper. A docker image is provided but you may use any if the above requirements are met." Sources: https://docs.vast.ai/guides/serverless/comfy-ui , https://github.com/vast-ai/pyworker/tree/main/workers/comfyui-json
- **Models**: custom models/nodes are installed via the template's `PROVISIONING_SCRIPT` (runs at instance creation) or baked into a custom image; the ComfyUI serverless guide expects models and nodes to be pre-installed before serving. Sources: https://docs.vast.ai/guides/templates/creating-templates , https://docs.vast.ai/guides/serverless/comfy-ui . Vast **volumes** are *not* an answer for serverless model caching: "A volume is physically tied to the machine it was created on" — local-only, no cross-machine attach. Source: https://docs.vast.ai/guides/instances/storage/volumes
- **Cold-start model**: worker lifecycle is Creating → Starting → Loading/Model-Loading → Ready; scaled-down workers go Stopping → **Inactive (STOPPED)** — i.e. a *stopped instance whose disk (with models) is retained*, so re-activation is an instance start + model load, not a fresh download. "Stopped: model loaded, ready to activate on-demand." Sources: https://docs.vast.ai/guides/serverless/worker-states , https://docs.vast.ai/guides/serverless/setting-up-endpoints . Only *new* workers pay the full provisioning download. The engine keeps a cold pool sized by `cold_mult` (default 3× current load) to absorb spikes without full cold starts. Source: https://docs.vast.ai/guides/serverless/setting-up-endpoints
- **Cold-start caveats for multi-GB SeedVR2 models**: (a) docs give no timing guarantees — even the 8 GB LLM quickstart says expect 3–5 min for first readiness (https://docs.vast.ai/guides/serverless/setting-up-endpoints); a ~10–20 GB provisioning download on a fresh worker will be longer and *is billed* (Loading is a billed state — https://docs.vast.ai/guides/serverless/pricing). (b) Restarting a stopped instance on Vast can block if the GPU was meanwhile rented by someone else — the instance sits in "scheduling" until the conflicting job ends (https://docs.vast.ai/guides/instances/manage-instances); this marketplace risk applies to Inactive workers and is presumably why the engine over-provisions the cold pool. Mitigations in §6.

## 3. Input/output for ephemeral workers; payload limits

- Yes — the platform's ComfyUI story assumes **S3-compatible object storage** for outputs, exactly as our wrapper documents: the template "allows you to send requests to ComfyUI and have generated assets automatically uploaded to S3-compatible storage", configured via `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET_NAME`, `S3_ENDPOINT_URL`, `S3_REGION` env vars or a per-request `input.s3` object (request-level overrides env). Responses carry a pre-signed download URL per asset. Sources: https://docs.vast.ai/guides/serverless/comfy-ui , https://github.com/vast-ai/pyworker/tree/main/workers/comfyui-json (README, Request Fields)
- Request shape (comfyui-json worker, route `/generate/sync`): `{"input": {"request_id": "<uuid, optional — generated if absent>", "workflow_json": {...} | "modifier"+"modifications", "s3": {...}, "webhook": {"url": ..., "extra_params": {...}}}}`. `__RANDOM_INT__` placeholders are substituted per run. Source: comfyui-json README (URL above). This is bit-for-bit the contract our POC wrapper exposes (`input.request_id`, `s3` config) — the POC wrapper is the ai-dock wrapper family.
- **Inputs**: the ai-dock ComfyUI API Wrapper downloads any workflow string that parses as a URL "into ComfyUI's `input/` directory" (MD5-hashed cache) and substitutes the local filename — so source videos are passed as URLs (e.g. presigned S3 GET), never as request bytes. Outputs: S3 presigned URLs, opt-in inline base64, and/or a webhook POST. Source: https://github.com/ai-dock/comfyui-api-wrapper (README)
- **Payload size limits**: none documented at platform level. The `/route/` call carries only routing metadata; the job payload goes directly to the worker, whose aiohttp server is created with `client_max_size=0` (size cap disabled) — source: `vastai/serverless/server/lib/server.py` in https://github.com/vast-ai/vast-sdk . Practically, keep payloads to workflow JSON + URLs; move bytes via object storage in both directions.

## 4. Pricing, GPU selection, concurrency, maturity

- **Pricing**: "pay-per-second pricing for all workloads at the same price as Vast.ai's non-Serverless GPU instances" — no serverless markup; recruited workers add their market rate to the running sum. Billed states: Ready and Loading; Creating and Inactive are *not* billed for compute; storage + bandwidth are billed in all states except Destroyed. Source: https://docs.vast.ai/guides/serverless/pricing . On-Demand, Interruptible and Reserved pricing types are supported. Source: https://vast.ai/products/serverless
- **GPU selection**: full marketplace filter via workergroup `search_params` (same fields as offer search: `gpu_name`, `num_gpus`, `gpu_ram`, `dph_total`, `reliability`, `verified`, …) plus the `gpu_ram` floor. Availability is marketplace-dependent — strict filters (e.g. only 48 GB cards in one region) shrink the recruitable pool. Sources: https://docs.vast.ai/guides/serverless/workergroup-parameters , https://docs.vast.ai/api-reference/search/search-offers
- **Concurrency**: per endpoint, bounded by `max_workers` (default 16, configurable). Per worker, the ComfyUI worker is **serial**: "ComfyUI does not handle concurrent workloads and there is no current provision to load multiple instances of ComfyUI per worker node" (fixed cost 100, FIFO). So throughput ≈ number of Ready workers. Sources: https://github.com/vast-ai/pyworker/tree/main/workers/comfyui-json (README), https://docs.vast.ai/guides/serverless/setting-up-endpoints , open enhancement issue "Allow parallel requests on ComfyUI worker" https://github.com/vast-ai/pyworker/issues/60
- **Maturity**: Serverless launched late 2025 — "The headline story of 2025 was the recent launch of Vast.ai Serverless" (https://vast.ai/article/vast-ai-2025-year-in-review , https://vast.ai/article/vast-ai-serverless-automated-gpu-scaling). Docs are current (llms.txt index maintained; docs repo pushed 2026-08-26). PyWorker repo: active first-party maintenance (last push 2026-08-24, e.g. "Split openai worker into per-engine backends"; ComfyUI benchmark race fix 2026-06-05) but a small community (19 stars, 34 forks, 9 open issues incl. #60 above and #38 "Handle errors from model for comfyui-json") — data via GitHub API on 2026-08-27, https://github.com/vast-ai/pyworker . Net: young but first-party-supported; expect to read source (as this research had to for `/route/` mechanics — the docs don't spell out the wire protocol).

## 5. Fallback: DIY autoscaled pool over the REST API

The plain REST API covers the full instance lifecycle (all with `Authorization: Bearer $VAST_API_KEY`); the POC's `GET /api/v1/instances/` generalizes to:

| Operation | Endpoint | Notes | Source |
|---|---|---|---|
| Search offers | `POST https://console.vast.ai/api/v0/bundles` | JSON filters with `eq/neq/gt/gte/lt/lte/in/notin` over `gpu_name`, `num_gpus`, `gpu_ram`, `dph_total`, `reliability`, `verified`, `rentable`, `type` (`ondemand`/`bid`/`reserved`); returns `{"offers": [...]}` | https://docs.vast.ai/api-reference/search/search-offers |
| Create instance | `PUT /api/v0/asks/{offer_id}` | body: `image` (or `template_hash_id`), `disk`, `env`, `onstart` (≤4048 chars), `runtype`, `price`, …; returns `{"success": true, "new_contract": <instance id>}` | https://docs.vast.ai/api-reference/instances/create-instance |
| Start / stop | `PUT /api/v0/instances/{id}` | body `{"state": "running"}` / `{"state": "stopped"}` | https://docs.vast.ai/api-reference/instances/manage-instance |
| Destroy | `DELETE /api/v0/instances/{id}` | "irreversible and will delete all data" | https://docs.vast.ai/api-reference/instances/destroy-instance |
| List/status | `GET /api/v0/instances/` (POC uses the v1 alias) | poll `actual_status` for readiness | https://docs.vast.ai/api-reference/instances |

That is sufficient to build our own pool manager (search → create from template → poll ready → drive ComfyUI directly as the POC does → stop/destroy on idle). Cost of this path: we re-implement everything serverless already does — recruitment, benchmarking/bad-host screening, cold pools, retry-on-dead-worker, queue-aware scaling — and we still face the stopped-instance GPU-reclaim risk when using stop/start for warmth (https://docs.vast.ai/guides/instances/manage-instances).

## 6. Verdict and integration sketch

**Fit-with-caveats — use serverless as the primary path.** The platform's own ComfyUI serverless stack already is our POC wrapper's contract (S3 delivery, `input.request_id` correlation, URL-fetched inputs, webhooks), the autoscaler solves the hard parts of marketplace GPU management (recruitment, benchmarking-out slow hosts, cold pools, per-second billing at plain on-demand rates, scale-to-zero via inactivity timeout), and the wire protocol is trivially callable from .NET without the Python SDK.

Caveats to engineer around:

1. **No .NET SDK** — implement the 2-step protocol from §1 in a small C# `VastServerlessClient` (route → poll → worker POST with `auth_data`; re-route on connect failure). ~200 lines; the contract is verified against `vast-sdk` source.
2. **Cold starts with multi-GB SeedVR2 models** — bake models into a custom image (registry pull is typically faster and more reliable than N provisioning downloads, and identical across workers) or keep a pinned `PROVISIONING_SCRIPT`; size `min_workers`/`cold_mult` so spikes hit Inactive (stopped, model on disk) workers rather than fresh Creates; accept that a fresh worker's Loading time is billed and that Inactive→Ready can stall if the host GPU was re-rented.
3. **Serial workers** — one upscale job per worker at a time; size `max_workers` to peak parallel jobs; keep the fixed `cost=100` model (or fork the workload calculator to scale with pixels×frames for better capacity estimates).
4. **Long jobs** — `/generate/sync` blocks; the SDK default worker timeout is 600 s. For upscales that can exceed that, pass a larger worker-call timeout in our client and/or rely on `input.webhook` + S3 as the durable completion signal, treating the HTTP response as best-effort.
5. **Young platform** — keep the DIY fallback (§5) as a designed-but-unbuilt seam: hide dispatch behind an `IUpscaleDispatcher` so a `ServerlessDispatcher` (route+worker POST) and a `ManagedPoolDispatcher` (offers/create/stop/destroy + direct ComfyUI wrapper calls) are interchangeable. The job contract (workflow JSON in, `request_id` correlation, S3 URLs out, webhook) is identical in both worlds — which is the strongest argument that adopting serverless now costs us nothing if we later have to fall back.

Proposed serverless setup:

- **Template**: custom image = Vast ComfyUI base + SeedVR2 custom nodes + SeedVR2 models baked in + ai-dock API wrapper; env: S3_* pointed at our bucket, `PYWORKER_REPO`/`PYWORKER_REF` pinned to our fork of `workers/comfyui-json` with a SeedVR2 `benchmark.json` (screens out hosts too slow for video upscaling — see calibration guidance in the comfyui-json README).
- **Endpoint/workergroup**: `search_params` filtering `verified`, `reliability >= 0.99`, `gpu_ram` ≥ SeedVR2's requirement, acceptable `dph_total`; `min_workers` low, inactivity timeout on for scale-to-zero, `max_workers` = peak concurrent jobs.
- **Backend flow**: .NET job service uploads source video to S3 → builds workflow JSON referencing a presigned GET URL → `POST run.vast.ai/route/` (cost 100) → `POST {worker}/generate/sync` with `{"auth_data": ..., "payload": {"input": {"request_id": <job id>, "workflow_json": ..., "s3": {...}, "webhook": {...}}}}` → completion via webhook/S3 presigned URLs, correlated by `request_id`.
